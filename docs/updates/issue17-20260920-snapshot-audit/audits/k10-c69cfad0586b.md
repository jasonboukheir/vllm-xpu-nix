## Requirement and effective behavior

For Brutus/Arc Pro B70 native D256/Q24/KV4 attention, reduce synchronization while combining sixteen split outputs and applying inverse H256. This benefits short K4V2 MTP verification, whose three virtual rows select sixteen splits at 4096–8192 tokens; batch-two and fixed-sixteen callers also reach it. It does not implement DFlash2’s D128/windowed draft.

The entire production delta is 139 insertions/one deletion in `csrc/xpu/attn/xe_2/kvarn_decode.hpp`: add `KVarNReduceSplit16FourColumnOutputHadamardKernel`, then select it in `KVarNDecodeD256G128DpasQ6PrefetchRecordCursorConfig::launch` when `unrotate_output && num_kv_splits == 16`. k11 changes no byte of this file. Other split counts, unfused reduction, producer arithmetic and cache formats retain their previous paths.

The new reducer uses 64 threads, each owning dimensions `t,t+64,t+128,t+192`, instead of 256 one-column threads. Its explicit workgroup barriers fall from ten to four, and the LSE maximum becomes a subgroup reduction. Shared storage remains sixteen weights plus 256 float outputs: 1088 bytes. No allocation/schema change accompanies it.

## Correctness and ownership

The subgroup width is statically 16 and explicitly requested by the launch policy. Under the caller invariant `1 <= seq_lens[b] <= max_seq_len`, `active_splits <= 16`. Consequently subgroup zero owns every potentially valid LSE; other subgroups neither read active statistics nor write weights. Its sixteen threads write distinct weights, followed by a workgroup barrier before consumption. Lowest-float sentinels become zero weights; the skip occurs before reading poisoned inactive partials.

Each column accumulates splits in ascending order with the original numerator/denominator arithmetic. H256 stages 0–3 exchange subgroup lanes using XOR; the upper lane computes partner-minus-self, preserving butterfly signs. The 256 register results are stored once and fenced. For stages 4/5, `pair_thread=t,t+64` enumerates all 128 butterfly pairs exactly once: each pair reads/writes disjoint low/high locations. No synchronization is needed between those two disjoint rounds; the barrier after each stage protects the next stage’s reads. Stages 6/7 use each thread’s four registers; final stores also have unique ownership. No cross-workgroup shared storage exists.

Both FP16 rounding boundaries remain: after weighted reduction, then after H256 normalization by 1/16. BF16 output converts that second FP16 result. The denominator still assumes at least one finite valid split; zero-length rows are outside the existing wrapper contract, not newly supported. V2 dummy/padded rows must respect that contract. Source reasoning is not a device race proof.

## Retained measurements and limits

Artifacts below are under `benchmark-results/kvarn-k4v2/20260913T051252Z/`. I independently parsed all four `reducer16-four-column-short-arm{1-baseline,2-prototype,3-prototype,4-baseline}/results.json`, verified their SHA256 values against the retained review, recomputed medians from raw samples and compared output hashes: **216 comparisons, zero mismatches; critical-cell geometric speedup 1.03032884**. The six cells use contexts 4096/4224/4352, three virtual rows, sixteen splits and 11/17 resident blocks. Each cell has five samples of sixty calls after 200 warmups. These are XPU event spans including submission gaps, not isolated reducer duration or model throughput.

The measured prototype `402d92b2afb3df17760f63cb182a1c584281033f` has byte-identical `kvarn_decode.hpp` to k10, checked through its retained Git worktree. `reducer16-four-column-installed-delta.json` records identical 3004 vLLM files and only the attention DSO changed among thirteen kernel-package files. The retained installed-test log reports 545 passes.

Limitations remain explicit: `reducer16-four-column-broad-review.json` records 348 exact comparisons but failed fresh-start repeatability, with 17.53%/16.91% worst baseline/prototype variation. The order-controlled review records 96 exact comparisons and repeatability within 3.99%, but one K4V4 B2/4K/split16 comparison regresses 3.67%, exceeding its 3% bound. Do not relabel those failed gates. The release’s later 39–51% native improvement belongs to k11’s block loads, not k10.
