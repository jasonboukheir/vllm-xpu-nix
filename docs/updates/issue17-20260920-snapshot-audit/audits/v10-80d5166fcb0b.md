## Requirement and retained behavior

The change makes `kvarn_k4v2_g128_compact` a usable XPU storage format, rather
than merely a quantizer preset. It registers uint8 storage/quant-mode 105,
extends DPAS value packing and reconstruction, passes the value width through
native writer/decode/materialization, and admits compact K4V2 bundled MTP.
For D256/G128, four-bit keys occupy 16,384 bytes, two-bit values 8,192, and
unchanged scale/zero-point metadata 2,304: **26,880 bytes per block/head**,
versus 35,072 for K4V4. BF16 compute and FP16 resident tails remain distinct
from compressed storage.

`kvarn_attn.py:KVarNMetadataBuilder._lifecycle_policy` retains eight recent
full blocks after flushing at the sixteen-block high-water mark. This improves
the two-bit history policy without increasing the existing sixteen-block
prefill reservation. K4V4 keeps four/zero. This is bounded quantization
residency, not sliding-window attention.

`triton_kvarn_decode.py:_kvarn_native_split_count_cached` selects sixteen splits
for exactly three K4V2 rows at inclusive context extents 4096–8192, including
MTP2 virtual rows; other batch/context choices and 32-split scratch capacity
remain unchanged. `_kvarn_build_packed_kv_kernel` uses `(pages, requests,
heads)` launch axes, removing page count from constexpr specialization.
Both behavior changes survive the final released tip and have no demonstrated
upstream replacement.

The released workload is Brutus/Arc Pro B70, RedHat Qwen3.8-27B W4A16/BF16,
K4V2 target plus K4V2 bundled MTP2, four slots and retained vision. The owning
feature is v05 `fcab69494f1719e91e416aace17ef6ad501fe900`.

## DFlash2 boundary

`_resolve_kvarn_cache_layout` permits DPAS only for D256/G128/K4V4 or K4V2;
native admission additionally requires Q24/KV4 and zero sliding window.
Kernel `kvarn_decode_xe2.cpp` hardcodes those dimensions. Generic configuration
can calculate D128 record bytes, but that does not supply a working native
writer/reader/attention path. Syvai requires D128/Q32/KV8, noncausal draft
blocks and window 2048. Implement a compatible D128 route and windowed
allocation/masking without reinterpreting D256 records. The platform currently
skips sliding layers, defeating all-K4V2 drafting unless correctly adapted.

V2 DFlash inserts context K/V before `_build_uniform_attn_metadata`; exact
reservation, commit/rejection and ownership semantics must precede those
writes. Neither v10's recent-history window nor relaxed startup guards solves
this. Preserve D256/MTP/vision while adding the distinct draft contract.
