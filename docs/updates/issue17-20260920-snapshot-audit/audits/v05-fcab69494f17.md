## Requirement and final released behavior

This is a large owning feature commit (72 files, 19,521 additions, 363
deletions), not one isolated kernel workaround. Its effective requirements are:

1. KVarN tile quantization with Hadamard transforms, Sinkhorn balancing, packed
   records, permanent compressed history and bounded FP16 sink/recent/tail
   storage; native Xe2 reads/writes and the supporting reference paths.
2. Separate physical attention and recurrent-state allocation/block namespaces
   for Qwen hybrid models. A fixed 128-token compressed tile must not be
   enlarged to match a recurrent-state page. Admission, null pages, zeroing,
   copies, cancellation/reuse, warmup and capacity must all honor those pools.
3. Correct speculative history: only committed tokens may enter permanent
   compressed history; rejected speculative rows remain replaceable. One
   metadata-builder owner controls each layer group's mutable slots/flushes.
4. The qualified native current-stream QKV frontend, shared flush indices,
   native materialization and bound decode plan preserve measured performance.
5. Correct profile/configuration selection, quantized dtype registration,
   deterministic oneDNN policy, retained Qwen images, and bundled MTP.

Follow-ups changed the release contract substantially. Final old release is
K4V2 target **and** K4V2 bundled MTP2 draft, BF16 compute/W4A16 weights,
RedHatAI/Qwen3.8-27B-INT4 at revision
`bf08f3dbd9a324e53956920aad378a1f1b6dd24a`, Arc Pro B70, eager V1, four slots,
2,048 prefill tokens, prefix caching off and two images. Do not replay the
original B1/K4V4-only contract.

The separate request-stable projection/norm feature is much narrower than the
release above: `_is_xpu_kvarn_request_stable_profile` in
`model_executor/determinism/request_stable_linear.py` explicitly selects the
AEON model ID and revision `6b0622f4354481d5d04577d48ba0db844efc1330`, eager
V1, no speculation, language-only, no prefix cache and restricted parallelism.
It is **inactive** for the released RedHat MTP/vision profile and the requested
syvai V2 profile. Its 64-row projection slicing is not a hidden prerequisite
for DFlash2. It still represents an independently implemented correctness
requirement; inactivity here is not evidence that its historical requirement
has been retired or covered upstream.

## Disposition: ADAPT; minimum residual and cleanup boundaries

Keep the owning cache feature, its independent pool/lifecycle guarantees, and
the released native performance path. Fold its later repairs into a coherent
final implementation; no evidence supports deleting KVarN or substituting
TurboQuant. The minimum port consists of dtype/spec/backend selection,
record/quantization/attention operations, allocation/accounting, pool-qualified
scheduler/worker lifecycle, and exact V2/speculator ownership/update semantics.

Specific changes required for the requested profile:

- Replace the hard V1 gates in `config/vllm.py`,
  `platforms/xpu.py:_check_kvarn_beta_unsupported_config` and
  `xpu_worker.py:_check_kvarn_worker_model_runner` with the actually qualified
  V2 DFlash2/MTP configuration contract. These gates are superseded **only once
  the port is correct**. Do not remove unrelated graph/prefix/geometry guards
  just to get past startup.
- `KVarNMetadataBuilder.build` currently computes committed history as
  `seq_len - query_len`; obtaining `seq_lens_cpu` falls back to device
  `.tolist()`, and `_kvarn_block_table_numpy` falls back to `.cpu().numpy()`.
  V2 gives live device metadata. Design an exact accepted-history bridge,
  retain pinned staging lifetime safety, and measure its synchronization cost.
  Never substitute `seq_lens_cpu_upper_bound` for committed length.
- Exclude draft layers from target mutable KVarN builders using the existing
  `active_layer_names` mechanism; retain dedicated draft builders. Account for
  DFlash context K/V insertion before draft query metadata and for noncausal
  draft query blocks. Test causal/window semantics, not just accepted startup.
- Add real compact D128/G128 support and sliding-window semantics for syvai.
  Released native admission/layout helpers require the Xe2 D256/G128/Hkv4
  geometry. `KVarNAttentionBackend` inherits `supports_sliding_window=False`,
  while XPU configuration adds `sliding_window` to dtype-skip layers. Those
  defaults would defeat all-K4V2 drafting. Remove the skip only where the new
  backend, scheduler and kernels actually implement it.
- Carry per-pool null initialization, `KVBlockZeroer.zero_block_ids_by_group`,
  `zero_mamba_block_ids`, group-qualified `KVCacheBlockCopy`, capacity checks,
  and `_WarmupBlockAllocator` into current upstream helpers. The v05 V2 warmup
  edits are useful partial groundwork, not an already-working V2 port.

Safe minimization identified by source evidence:

- The obsolete `use_trusted_qlen1_inline_plan` branch in
  `unified_qkv_attention_with_output` has no producer anywhere in released
  `vllm`; `forward_trusted_qlen1_inline` has no implementation there. Remove
  that dead alternative when folding the feature. This does **not** justify
  deleting `KVarNTrustedNativeDecodePlan`: the released decoder still uses it.
- `_metadata_lifecycle_variant` is assigned/logged only, and
  `_kvarn_metadata_lifecycle_requested` always returns `reference`.
  `_kvarn_forward_pool_ensure_requested` always selects `always`.
  Selector indirection/log labels may be simplified while preserving the
  current full rebuild and pool-ensure behavior. Retired environment checks
  still prevent stale launch configurations; do not silently revive variants.
- The active `bound_native_v2` plan, `use_bound_qlen1_inline_plan_v2`,
  `unified_qkv_attention_with_output`, and current-stream native scatter are
  **not** superseded scaffolding. Here “v2” names an internal decode-plan
  implementation, not Model Runner V2. They are selected by the released
  compact profile and must retain their benefit or be replaced by a measured
  equivalent.
- Do not carry a new duplicate DFlash RMSNorm workaround over upstream
  `48f663c37f`. Do not revive removed upstream CPU metadata fields or overwrite
  current warmup/JIT, fast-prefill, HiSparse, or transfer behavior.
- The inactive AEON request-stability path can be separated into an
  independently explained feature commit if that improves reviewability.
  Dropping it needs a scope-retirement decision or demonstrated replacement;
  this audit supplies neither. Similarly, CUDA/reference implementations and
  noncompact presets are not proven redundant simply because Brutus takes the
  native compact path.

### Follow-up: remaining V2 scalar-pool assumptions

Verified against the frozen target and the released v05-containing stack;
allocation-only adaptation would leave concrete consumers inconsistent:

- `gpu/attn_utils.py:init_kv_cache` calls
  `worker/utils.py:allocate_kv_cache` for ordinary device allocation. The latter
  still asserts all tensor sizes equal and creates one `buf`, even though it
  now obtains each tensor's count through `KVCacheConfig.num_blocks_of`.
  `num_blocks_of` only distinguishes host versus device. Both backing identity
  and block count must follow the new device pool; changing one is insufficient.
- `GPUModelRunner._init_kv_zero_meta` supplies scalar
  `kv_cache_config.num_blocks`; `KVBlockZeroer.__init__` divides each layer's
  leading dimension by that count. Runner request updates then call the flat
  `zero_block_ids` and `copy_kv_cache_blocks_inplace(self.kv_caches, num_blocks,
  ...)`. Restore group-qualified dispatch/counts together, or a local block ID
  can address the wrong backing/stride. The existing v05 fixes address these
  old call sites but must be reconciled with target APIs and draft ownership.
- `gpu/warmup.py:run_mixed_prefill_decode_warmup` and `_warmup_kernels` sum
  group demand against one count and use one incrementing `_alloc_blocks`
  closure across all groups. Restore the per-pool allocator/admission logic.
  The surviving `KVBlockZeroer.warmup(kv_cache_config.num_blocks)` call also
  needs checking against actual per-pool coverage; v05 did not replace it.
- `gpu/input_batch.py:set_dummy_context` accepts scalar `num_kv_blocks` and
  wraps every group's synthetic IDs modulo `num_kv_blocks * bpk`, including
  block zero. `GPUModelRunner` still passes scalar `kv_cache_config.num_blocks`
  even in the released stack. A minimum-count alias may stay in bounds but
  folds a large attention context onto the small recurrent pool's count and
  null page; it does not establish realistic KVarN profiling history. Adapt
  synthetic context ownership/initialization or explicitly exclude that helper
  from credible performance evidence. No corruption was dynamically observed.
- `gpu/cudagraph_utils.py:_init_minimal_kv_cache_for_profiling` sets a scalar
  `num_gpu_blocks_override`, invokes `get_kv_cache_config_from_groups` with
  `available_memory=0`, then writes `minimal_config.num_blocks` back to cache
  config. This bypasses the higher-level override-to-byte-budget conversion
  expected by v05 independent pools. If graph-memory profiling is reachable,
  supply valid per-pool minimal reservations; otherwise preserve an explicit
  unsupported guard. Eager-only qualification need not enable graphs.

The cross-layer assignment `kv_caches[layer_name] = kv_caches[target]` in
`init_kv_cache` is intentional model KV sharing, not by itself a single-pool
bug. `gpu/block_table.py:BlockTables.num_blocks` is a per-group/per-request
table-length array, not a scalar physical-capacity alias. Do not rewrite either
merely because its name resembles the problematic scalar. These are static
findings and proposed residual checks, not new runtime validation.

### New bounded-draft work, separate from existing-feature replay

The released allocation contract has recurrent reservations for runner slots
and growing attention pools with equal token capacity. It can be replayed with
its old MTP behavior, but that policy must not be described as DFlash support.
The new D128 sliding draft needs an additional independently sized category:

`budget = all pool null bytes + runner-slot recurrent reservation + runner-slot
bounded draft reservation + growing shared target attention allocation`.

For each compatible draft group, use actual layer count, D128 record page bytes,
and the spec's maximum simultaneously held physical pages. Target
`SlidingWindowSpec.max_admission_blocks_per_request` computes
