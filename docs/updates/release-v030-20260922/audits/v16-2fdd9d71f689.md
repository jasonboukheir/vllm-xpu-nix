## Actual v0.30 coverage and residual

Upstream `5fe77aecfc7687c1f3cc49862022ce34d45d1784` is an ancestor of the
selected tag. Its diff removes `CommonAttentionMetadata._seq_lens_cpu`,
`._num_computed_tokens_cpu`, their public properties, proposer copies,
invalidations and increments. This covers the obsolete duplicate-shadow
portion of v16. It does **not** cover independent advancement of the surviving
bound:

- `vllm/v1/spec_decode/llm_base_proposer.py:815` still checks the bound and
  line 816 still performs `seq_lens_cpu_upper_bound += 1` in
  `_update_positions_dependent_metadata`.
- `prepare_inputs_padded`, line 1146, passes the caller's bound directly into
  a new metadata object; it likewise borrows device lengths and query starts.
  This is a live alias, not an independently owned CPU snapshot.
- `GPUModelRunner._build_attention_metadata`, line 2379, takes a slice of
  `self.optimistic_seq_lens_cpu`; line 2462 passes it to common metadata.
  `_prepare_inputs` computes that buffer assuming all prior draft tokens
  were accepted (lines 2088–2096).
- Unpadded `prepare_inputs` already allocates `new_seq_lens_cpu` by subtracting
  the actual rejected counts from the CPU upper bound (lines 1200–1203), and
  uses that result in the new metadata. The old exact/bound double increment
  is gone there. It does not repair the padded alias path or preserve retained
  references to the surviving bound during later in-place advancement.
- `set_inputs_first_pass` can return the same common metadata object when no
  extra input slots are needed. Out-of-place tensor rebinding protects tensor
  storage and prior snapshots; it does not promise that the metadata object
  itself is immutable. v16 also never isolated intentionally updated device
  tensors. Do not overstate this repair as complete target/draft ownership.

Target `vllm/v1/attention/backend.py:443` explicitly says the CPU bound is
optimistic during async speculative decode and unsafe as an exact per-row
context length. Removing the old shadows does not justify treating that bound
as committed history.

The **existing released KVarN builder already has a correct exact-source
fallback**. At released `vllm/v1/attention/backends/kvarn_attn.py:1179–1180`,
`getattr(cam, "seq_lens_cpu", None)` falls back to `cam.seq_lens.tolist()`.
On v0.30 the removed property is absent, so that path reads current device
lengths. It combines those with CPU query boundaries, using
`max(seq_len - query_len, 0)` for allocation and permanent-flush eligibility
(lines 1254, 1312 and 1449). Preserve this exact source; do not substitute
`seq_lens_cpu_upper_bound` or resurrect the deprecated fields. A minimal port
may use the direct device-length read and update the obsolete cached-copy
comment. No new exact-shadow API is needed to make this behavior work.

## Disposition, fold and dependencies

**ADAPT, folded into the v05 KVarN feature commit.** Retain only this residual
production change in `_update_positions_dependent_metadata`:

```python
if common_attn_metadata.seq_lens_cpu_upper_bound is not None:
    common_attn_metadata.seq_lens_cpu_upper_bound = (
        common_attn_metadata.seq_lens_cpu_upper_bound + 1
    )
```

Do not reintroduce the two deleted exact-shadow assignments or fields. Keep
the builder's exact device-length fallback and genuine query boundaries. A
later synchronization reduction must prove validity through rejection,
reordering and each draft step; it is not necessary for initial correctness.

Fold with v05 `fcab69494f1719e91e416aace17ef6ad501fe900` and coordinate
v11 `73fb9e7aa230e9d6164c810a05175bd342995565` for exclusive mutable draft
builder ownership. v10 `80d5166fcb0b7935f3f95b8d343e3e669940261f` supplies the
K4V2 feature exercised by the regression. v15's BF16-draft admission is not
a prerequisite. No kernel schema/ABI change originates in v16; existing
paired KVarN k08/k09 operators remain dependencies of the owning feature.
This is not a reason to restore the issue17 snapshot's V2 implementation.

## Required replay and qualification gates

Adapt the existing `test_llm_base_proposer.py` regression, replacing the now
irrelevant exact-shadow parameterization with same-object/overlapping-view/
separate/missing **surviving-bound** coverage. Preserve two draft steps,

retained prior snapshots. Deliberately optimistic bounds must remain distinct
from live lengths. Do not populate removed fields just to satisfy old tests.

Extend the existing KVarN attention suites at the cheapest meaningful level
to prove builders use actual device lengths even when upper bounds are larger.
Exercise accepted/rejected MTP around 127/128/129, ragged/concurrent batches,
target versus draft builders, cancellation/reuse and prefill-to-decode
transitions. Assert flush eligibility and packed/resident cache contents,
not merely the values of CPU metadata. Retain the installed XPU MTP test
`test_dpas_mtp_verify_masks_future_and_overwrites_rejected_tail` and paired
final-package MTP/vision/lifecycle qualification.

The device `.tolist()` fallback synchronizes once per metadata builder call,
with the resulting Python list reused across layers. Upstream removal of
prepopulated exact CPU copies can expose additional host synchronization
relative to the released stack. Measure matched old/new V1 MTP performance
and metadata cost; no magnitude is established here. Never replace exact
history with an optimistic bound to avoid a synchronization. The tiny host
out-of-place allocation also needs ordinary regression coverage, not a claimed
speed improvement. Any scoped exact-shadow optimization must preserve the
same rejection/ownership tests and have measured benefit.
