## Why this needs a port

Upstream made Model Runner V2 the default in v0.29.0 and targets removal of Model Runner V1 in v0.32; no calendar removal date is promised. This is the model runner, not removal of the entire `vllm/v1` engine namespace. [Upstream release notes](https://github.com/vllm-project/vllm/releases/tag/v0.29.0).

DFlash2's candidate selector is implemented in the V2 speculator. Our source deliberately rejects running DFlash2 through V1, which would omit that selector. Our KVarN integration separately rejects V2. Removing those guards alone is insufficient. [DFlash2 implementation PR](https://github.com/vllm-project/vllm/pull/52816).

| Verified finding | Consequence / owning repository |
| --- | --- |
| KVarN's builder consumes exact CPU sequence lengths and CPU block tables. V2 supplies live device lengths/tables and a CPU upper bound that can overestimate accepted history during asynchronous speculation. | **vLLM:** do not use the upper bound as committed length. Legacy CPU access introduces synchronization; design and measure the metadata bridge. |
| V1 excludes compressed draft layers from target metadata builders. V2 currently initializes target builders without that filtering, then initializes separate draft builders. | **vLLM:** establish one owner for each mutable tail/flush state; the shared initializer already accepts `active_layer_names`. |
| DFlash precomputes and inserts context K/V before building current draft attention metadata. KVarN metadata construction currently prepares mutable tail slots and flushes. | **vLLM:** compressed DFlash drafting needs an explicit cache-update lifecycle; normal MTP forward ordering is not sufficient. |
| The proposed Qwen DFlash2 draft uses D128 attention and sliding-window configuration. Current compact K4V2 XPU layout selection only accepts D256/G128, and KVarN does not advertise sliding-window support. | **Both source forks:** implement and qualify the draft geometry/layout and window semantics as part of the first K4V2 DFlash2 integration. |
| The released kernel source lacks the stacked RMSNorm per-layer weight fix; released vLLM also lacks the later per-layer fallback. | **Kernels / vLLM:** backport a verified fix before drawing acceptance conclusions. |
| Quantized DFlash projections require correct fused-module mapping and context-KV projection handling. | **vLLM:** integrate the required quantized draft fixes and verify actual XPU W4A16 dispatch; NVIDIA Marlin instructions are not an XPU execution path. |
| Service and acceptance tooling assumes V1 and MTP K=2. | **Packaging:** extend provenance, launch configuration, counters and diagnostics before calling results DFlash2 measurements. |
