## Requirement and final-old behavior

v05 admitted bundled Qwen MTP only with `scheduler.max_num_seqs == 1`.
v07 removes that conjunct and the error's `B1` wording from
`platforms/xpu.py:_check_kvarn_beta_unsupported_config`; it adds six admission
cases covering slots 1/4/16 and one/two speculative tokens. It changes no
scheduling, attention kernel, memory allocator or metadata ownership logic.
Consequently, accepting 16 slots is a configuration assertion, not evidence
that sixteen full-context requests fit B70 memory.

The final old release retains scheduler-controlled concurrency and expands
the compact formats. Its relevant profile is Arc Pro B70,
`RedHatAI/Qwen3.8-27B-INT4` revision
`bf08f3dbd9a324e53956920aad378a1f1b6dd24a`, W4A16/BF16 compute, K4V2 target
and bundled MTP2 draft, eager V1, TP1/PP1, four slots, 2,048 prefill tokens,
two bounded images and prefix caching disabled. The 262,144 per-request
ceiling does not multiply the shared attention pool by four. Issue #17
requires preserving MTP/vision while adding V2 K4V2 DFlash2; neither the B1
restriction nor the original K4V4-only envelope should return.

## Upstream coverage and alternate implementations

At the frozen target, `git grep -i kvarn -- vllm tests` has no matches.
The old-to-target `platforms/xpu.py` diff contains docstring changes and a
sparse-GELU priority adjustment, with no equivalent KVarN admission contract.
`XPUPlatform.get_attn_backend_cls` routes TurboQuant independently; its
`turboquant_attn.py:customize_spec` uses per-token slot sizing rather than
KVarN's compressed tiles and mutable tail/flush ownership. Its existence
does not replace this supported workload.

Upstream does provide the correct generic admission mechanism. Commit
`f730a93d2bf2cad3002578238d5a1035ee1f4177` adds `max_num_active_seqs`.
Target `core/sched/scheduler.py:126–133` retains `max_num_seqs` for runner
slots and defaults active admission to that value; the waiting-queue loop
uses the optional lower active cap. `config/scheduler.py` validates that
cap against runner capacity. Reuse this mechanism; add no KVarN scheduler.
Recurrent reservation must still match allocated runner slots, not silently
shrink to the optional active cap.

V2 has partial ownership infrastructure, not a complete replacement:
`gpu/spec_decode/speculator.py:DraftModelSpeculator.set_attn` supplies
`active_layer_names=self.draft_attn_layer_names` to the shared initializer.
However, `gpu/model_runner.py:initialize_kv_cache` computes target layer names
but does not pass them as `active_layer_names` when constructing target
builders. Its `draft_layer_names` argument controls fast-prefill eligibility;
`gpu/attn_utils.py:init_attn_backend` filters ownership only through
`active_layer_names`. Thus mutable draft KVarN layers still need exclusion
from target builders during the V2 port.

## Disposition and dependencies

**ADAPT, folded into v05.** Preserve scheduler-owned concurrent admission and
its regression coverage within the final KVarN configuration contract. No
standalone scheduler implementation or repair commit is needed. Replace the
old V1-only envelope only alongside the working V2 port; retain other
unsupported-mode checks until their requirements are implemented and tested.

Dependencies identified by the paired inventory:

- v05 `fcab69494f17` owns KVarN; kernel k08 `9bb1e2d428b8` supplies its native
  operators. v07 adds no schema or ABI change.
- v08 `3b6c822e8a4f` repairs initial admission/auto-fit estimates to reserve
  recurrent state for every scheduler slot. Release-only v13 `d6cb2e6cb2de`
  preserves those reservations with attention-capacity overrides.
- v11 `73fb9e7aa230` isolates V1 draft metadata ownership; preserve its
  invariant using V2's existing filtering interface.
- v14 `32289022a4e3` bounds multi-request MTP materialization by reusing
  scratch per request when aggregate history exceeds it. Permitting concurrent
  startup without this lifecycle/capacity behavior is insufficient.
- v10 `80d5166fcb0b`, v12 `6519bf709dbb` and v15 `2e010408b971` expand format
  admission. Preserve final supported behavior without making BF16 drafting an
  intermediate issue-17 milestone. v16 `2fdd9d71f689` repairs CPU metadata
  aliasing; upstream `5fe77aecfc7687c1f3cc49862022ce34d45d1784` removes those
  deprecated shadows. Port exact committed-history semantics, not obsolete
