## Requirement and behavior in the final old stack

The assigned commit contributes 75 files, 20,813 insertions and 371 deletions.
It is a feature stack, including reference implementations and tests, rather
than a small workaround. Its essential requirements are the compact K4V2/K4V4
record formats; native packing/store/readers; bounded higher-precision sink and
recent-token storage; quantization only of accepted history; independent
attention/recurrent capacities; pool-qualified block ownership; and stable
cache generation/reset behavior. Full uncompressed history would abandon its
memory benefit.

The actual stable rollback is xpu-v1.12.2: Intel Arc Pro B70,
`RedHatAI/Qwen3.8-27B-INT4` revision
`bf08f3dbd9a324e53956920aad378a1f1b6dd24a`, W4A16 weights, BF16 compute,
eager V1, compact K4V2 target and bundled MTP2, four scheduler slots,
2048 batched tokens, 262144 maximum context, two images, prefix caching and
an 8 GiB `IndependentCPUOffloadingSpec` arena with `active_only` GPU policy.
The manifest records 306688 shared attention tokens and preservation of the
262144 per-request limit. Four scheduler slots do not imply four full contexts.

Later commits change the final requirement materially:

- v06 `81dc387cf9a80e88468b7f77f7df8dfb71939921` enables the qualified
  Qwen compact-K4V2 prefix path, fixes an aligned MTP checkpoint boundary,
  and adds bounded retained recurrent reservations for GPU-resident caching.
- v07 `a76fbb1ce06d50159978786f70daf44c27847ddd` supplies the bounded
  variable-size CPU arena, pool-qualified transfers, compact-page
  materialization, FP16 sink sidecars and restore invalidation. Its
  `active_only` policy omits the extra idle GPU checkpoint reserve.
- v08 `dcba4007ef6af8ba143d2794c194c36b58397339` populates MTP cache
  pages with a zero-proposal forward at the context ceiling and ignores
  padded no-write MTP rows in KVarN fill/ownership decisions.

Do not restore v05's original blanket prefix/connector rejection while replaying
the full stack. Optional natural formats, K4V4, BF16-draft configurations and
scoped request-stable operators remain supported requirements unless explicitly
retired; their absence from the default RedHat profile does not justify deletion.

## Upstream coverage and minimum residual changes

A frozen-target `git grep` finds no `kvarn` implementation. The target's

packed FP4 format/backend, not KVarN ABI, equivalent capacity or demonstrated

`KVarNAttentionBackend`/builder/implementation, native dispatch, bounded

### Packed layout and allocation accounting — adapt to v0.32

`02e55d2af38adab51ec5ffb985063d355b20805b` changes the generic packed
layout implementation and removes the GLM-specific allocator. At the frozen
target:

- `_get_kv_cache_bytes_per_block(groups, layout)` requires the resolved layout.
- `_get_layer_block_stride(spec)` rounds each layer-outer page to its alignment.
- `KVCacheSpec.get_block_stride_alignment()` resolves integer/`MultipleOf`
  alignment requirements; reading `.block_stride_alignment or 1` directly is
  no longer valid for all specs.
- `get_kv_cache_config_from_groups` uses padded per-layer block strides and
  physical byte offsets. For layer-outer layouts, the offset increments by
  `len(layer_names) * layer_stride`; block-outer uses page bytes.

Adapt local `_plan_kv_cache_tensors` to use this algorithm **inside each physical
pool**, retaining `pool_id` and that pool's capacity. Forward `layout` at every
new helper call. Do not keep the old offset scaling formula, resurrect removed
`KpoolTailSpec`/GLM-special allocation, or replace independent pools with the
shared upstream buffer. Preserve upstream's resolved `kv_cache_layout`.

`f7999d2e4489126f1c21868699f3890021f01b73` changes
`_pool_bytes_per_block` to accept `vllm_config` and account for actual HiSparse
allocations. Forward the new config parameter in retained shared-pool paths,
capacity/override checks, null-page accounting and worker reconciliation.
`fe341a53dda00472c281a2d1f4bd34a74e7eae6e`'s HiSparse capacity reporting
and `d5f356dae093d2e47b97af7c9cd8d2fc1aedc56f`'s separate residency
ownership should remain intact. They do not cover independent KVarN pools.

Keep new `KVCacheConfig.hash_block_size` and `cache_hit_alignment_tokens`
fields when producing/replacing local configs.
`d8fa463e2ba751759a3534dd3ce11af92f1eed83` supplies shared partial-hit
alignment helpers (`partial_hash_hits_enabled`,
`resolve_cache_hit_alignment_tokens`) and fixes checkpoint proof boundaries.
These must coexist with per-pool admission and v06/v07 retention, with exact
overlap disposition owned by their audits. `cb6458c5ce61632524c0447d49790725c1e1d9a2`
removes deprecated Mamba mode `all`; do not reintroduce its branches from old
context while resolving conflicts.

## Explicit V2 / DFlash2 gap inventory

Upstream already owns DFlash2's model and candidate-selection algorithm:
`b389ac29465b33f9e9c534df221ea3c129e9793f` introduced it;
`qwen3_dflash2.py`, `gpu/spec_decode/dflash2/speculator.py`, and
`gpu/spec_decode/__init__.py` contain the frozen implementation. Config identifies
`DFlash2DraftModel` as requiring the V2 candidate-head path; silently running
V1 would degrade it to DFlash1. Use these implementations, not a local duplicate.
Presence in v0.32 is not a new claim that it was absent from v0.31.

1. **Capability gates and exact draft choice.** Old final
   `XPUPlatform._check_kvarn_beta_unsupported_config` accepts only bundled
   Qwen MTP1/2 with explicitly allowed cache precision, and rejects V2 and
   graph mode. `xpu_worker._check_kvarn_worker_model_runner` independently
   rejects worker-local V2 selection. Replace these with narrow, tested V2/
   DFlash2 capability validation after integration. Keep eager execution for
   initial qualification unless graph behavior is separately demonstrated.
   Pin the drafter's exact revision and compatible target/tokenizer settings.

2. **Exclusive mutable builder ownership.** Frozen V2
   `GPUModelRunner.initialize_kv_cache` calls `init_attn_backend` with
   `draft_layer_names=...`, but that argument only excludes draft layers from
   fast-prefill eligibility. It does not filter them out of target metadata
   groups. `DraftModelSpeculator.set_attn` creates another builder for the same
   draft layers using `active_layer_names`. Port V1's explicit exclusion of
   draft-owned KVarN layers, so only the draft builder mutates their allocator.
   When excluding those layers, ensure zeroing/warmup/transfer registration
   still includes both target and speculator groups.

3. **DFlash context writes precede metadata preparation.** Frozen
   `dflash/speculator.py::propose` prepares context/query slots, calls
   `_precompute_context_kv`, and only then builds uniform draft metadata.
   `qwen3_dflash.py::precompute_and_store_context_kv` directly calls
   `attn.impl.do_kv_cache_update`. KVarN claims layers, allocates slots and
   flushes accepted history in `KVarNMetadataBuilder.build`, before ordinary
   attention writes. Consequently a quantized DFlash draft needs an explicit
   pre-write lifecycle preparation covering its accepted context writes,
   including chunked prefills, before the precompute call. The query-only
   metadata call is too late and does not describe the whole context write.
   A separately budgeted BF16 draft avoids this particular KVarN draft-store
   issue, but must still pass capacity, offload and correctness qualification;
   it is not a free memory/performance substitution.

4. **Exact history and CPU mirror performance.** KVarN snapshots actual
   `cam.seq_lens.tolist()` and uses `seq_len - query_len` to protect rejected
   proposals from permanent quantization. Preserve that invariant. V2 builds
   actual GPU seq lengths and supplies CPU upper bounds; the latter cannot
   replace exact lengths. V2 CAM currently has no local `block_table_cpu`
   propagation; `_kvarn_block_table_numpy` falls back to
   `block_table_tensor.cpu().numpy()`. That can be correct in eager mode but
   introduces synchronization. A V2 mirror must follow gathered request order,
   new blocks, recycled slots and speculative correction. Do not use stale
   scheduler lengths or a request-state table before its gather.

5. **Wide target verification and non-causal draft attention.** Local
   `_native_verify_view` only accepts one request, causal cached queries of
   length 2 or 3. The upstream Qwen3.8 DFlash2 acceptance recipe uses seven
   speculative tokens, so the target verifies up to eight queries. Compact
   DPAS `_verify_decode_path` falls back to `_cached_multiquery_path` outside
   native eligibility. Preserve bounded materialization and measure it, or
   extend native verification with paired kernel tests. The backend advertises
   non-causal support and propagates full-context limits, but that does not
   imply the same native fast path supports it. Exercise all selected draft
   attention groups and causal modes; generic `_decode_path_slow` constructs a
   causal mask unconditionally, so do not expand into that route untested.

6. **V2 recurrent rollback and pool consumers.** Keep local group-qualified
   zeroing/copy payload handling in `gpu/model_runner.py`, per-pool warmup IDs,
   null pages and independent capacities. This schema is shared with other
   runners even while KVarN V2 is guarded. Preserve the target's new recurrent
   fixes: `0eac15270710ddb7f5296d7244fcd0496c2daa0f` routes all
   speculation-capable rows through the speculative path;
   `10cc2f6ae2c9ba7cc5841ece95e27d0562aef1bf` bounds GDN query widths;
   `8a26869bcad1ae4ab3069a7d2aece86c17c1c695` uses request slots for
   aligned state copies; `3d6853b32c7c872df00d9e3489f642dc22e974e0`
   seeds state indices using Mamba block size; and
   `124b89d5b7bbbf7599763858c247848e073b024a` fixes exact-boundary state
   indices. Reconcile with v01/v02 and native GDN audits, not old code replacement.

7. **RAM offload and context-ceiling completeness.** V2 has connector
   registration, pre-forward and post-forward fences; its existence does not
   prove KVarN sidecars and independently sized caches work there. Preserve
   v07's actual pool capacities, transfer ownership and KVarN hooks. Demonstrate
   complete target/draft pages at every published prefix boundary. v08's
   `_should_populate_offloaded_mtp_cache` exists only in V1 and is specific to
   bundled MTP; map its completeness requirement to V2/DFlash context precompute
   and context-limit slot masking rather than copying that condition blindly.
   Never restore a prefix whose draft cache was not actually populated.

8. **Lifetime and warmup.** Retain worker process-state reset before model
   load and lazy-tail allocation within the measured profiling window. V1
   explicitly resets profiling KVarN cache state; V2 has separate dummy,
   warmup, clear-cache and weight-reload flows. Wire equivalent lifecycle
   boundaries for target and draft and verify the first real request cannot
   inherit dummy owners or stale flush state. Preserve graph rejection until
   captured/replayed lifecycle is independently validated.

9. **XPU-specific DFlash cost and multimodal behavior.** In the frozen
   `qwen3_dflash2.py::_grouped_conv`, the fused custom op is used only for
   `hidden_states.is_cuda`; XPU uses the tensor fallback. This is an observation,
   not evidence the fallback is wrong. Measure it before any performance claim.
   DFlash declares `supports_mm_inputs=False`; determine how target image
   hidden states and draft inputs interact in the actual Qwen path, and retain
   existing image support through an explicit serving test. The upstream
   acceptance fixture uses NVFP4 target weights and `language_model_only=True`,
   not this W4A16/K4V2/XPU/multimodal profile.
