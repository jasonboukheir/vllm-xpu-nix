## Requirement and effective release behavior

The synchronous V1 runner aliases exact CPU lengths and their optimistic
bound; draft input preparation can preserve those aliases. Before v16,
`SpecDecodeBaseProposer._update_positions_dependent_metadata` increments
both in place. One device step therefore advances shared host storage twice
and modifies target-owned buffers. Released `KVarNMetadataBuilder.build`
uses exact lengths minus query lengths for tail allocation and permanent
flush eligibility; premature advancement can compress a partly written tile.

v16 independently rebinds all three host tensors: `_seq_lens_cpu`,
`_num_computed_tokens_cpu`, and `seq_lens_cpu_upper_bound`. Its eight cases
cover identical objects, overlapping views, separate/missing exact shadows,
ordinary/M-RoPE positions and two steps at lengths 127 and 61951. Device
execution and cache precision remain unchanged. No later fork commit
supersedes this release-only repair.

Preserve the B70 RedHat W4A16/BF16-compute, target/draft K4V2 MTP2 workload,
concurrency and vision. The requested V2 syvai DFlash2 path needs the same
history guarantee with different metadata ownership; no BF16 serving
milestone is required.

## Upstream coverage and remaining aliases

Upstream `5fe77aecfc7687c1f3cc49862022ce34d45d1784` removes the two exact
CPU fields and their properties. This eliminates their duplicate increments,
but **does not cover the whole repair**:

- Frozen V1 `llm_base_proposer.py:816` still performs
  `seq_lens_cpu_upper_bound += 1`. `prepare_inputs_padded` borrows the
  target's bound, device lengths, query starts and block table; its slot
  mapping is a view. Initial `set_inputs_first_pass`, without extra input
  slots, returns the same metadata object. The runner supplies a slice of
  `optimistic_seq_lens_cpu`. These paths still mutate target-owned host
  storage. Unpadded `prepare_inputs` instead subtracts rejected counts into
  a new host tensor and constructs new query starts/device lengths; that
  path no longer has the removed exact/bound double increment.
- V1 also intentionally updates borrowed device lengths when removing
  rejection padding and advancing drafts. v16 never isolated device tensors
  or metadata-object attributes. Do not describe its host repair as complete
  target/draft isolation, or retain borrowed views as immutable KVarN history.
- V2 already supplies the narrow semantic replacement.
  `gpu/spec_decode/speculator.py:DraftModelSpeculator._build_attn_metadata`
  allocates fresh zeroed CPU bounds, adds the absolute step into that separate
  destination, and clamps only the destination. This came from upstream
  `4ec199b66a791070348f3baf847b3a873c48cdd9`, which predates the old base.
  `_build_uniform_attn_metadata` delegates to it for autoregressive decode
  and DFlash; neither advances the caller's host tensor.
- V2 creates separate `InputBuffers`. Autoregressive
  `prepare_decode_inputs` reads target lengths/rejections and writes draft
  lengths; later `_update_draft_inputs_kernel` advances the draft buffer.
  Nevertheless, `AutoRegressiveSpeculator.propose` passes target-built
  `attn_metadata` directly into `_prefill`, and capture uses target builders.
  v11's dedicated compressed-draft owner must therefore build prefill
  metadata too. Filtering layers alone leaves missing entries.
- Shared `gpu/attn_utils.py:build_attn_metadata` passes views of bounds,
  query starts, device lengths, block tables and slot mappings across groups;
  `CommonAttentionMetadata.unpadded` similarly slices rather than cloning.
  V2 speculators also borrow `BlockTables`, whose slot mappings change during
  drafting. Treat these as live inputs, with explicit staging lifetimes.
  Both microbatch helpers clone host bounds before truncating them;
  `set_dummy_context` mutates an intentionally owned synthetic batch. Those
  mutations do not establish another production double-increment defect.

The surviving `_num_computed_tokens_cache` is a device-derived cached value,
not the removed CPU shadow. A new lifecycle must invalidate/rebuild derived
values when changing lengths/query boundaries; restoring deprecated fields
is unnecessary. The target explicitly documents CPU bounds as optimistic
under async speculation. Independent storage alone does not make them exact.

runner remains usable. Drop the two obsolete field assignments. On V2,

implementation and retain regression coverage for its ownership guarantee.
Do not revive V1 to satisfy the new configuration.

insertion, query writes, commit and reclaim must prevent flushes before
accepted context becomes resident. Keep adaptive verification, graphs and
prefix caching outside initial qualification. This is v05 lifecycle work,
not another copy of v16's three assignments.

`9bb1e2d428b8a25b262c0cd6704614bdf6ee3ad8` and k09
