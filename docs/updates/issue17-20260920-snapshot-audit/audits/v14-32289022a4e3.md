## Trigger, lifetime and numerical contract

`kvarn_attn.py:_cached_multiquery_overflow` runs only after materialization
raises `ValueError`. It requires DPAS, more than one request, aggregate lengths
above scratch capacity, and every individual length positive and within both
capacity and `md.max_seq_len`. A single oversized request remains unsupported;
this is not history tiling. Fitting batches, natural-layout dispatch and the
existing B1 native virtual-query fast path remain unchanged.

The helper checks query offsets start at zero, end at `q.shape[0]`, and each
query span lies between zero and its sequence length. Each nonempty request
receives its physical block-table row, sequence length, slot-mapping slice,
and zero-rebased query offsets through `dataclasses.replace`. It clears stale
batched FA/virtual-query plans and recursively uses the ordinary single-request
materialize/FA path. The new output is filled in original request order;
metadata and cache contents are not mutated by this helper. Empty query spans
are skipped. Catching `ValueError` does not establish overflow by itself: retain
the explicit eligibility checks and failure behavior for other invalid extents.

The same packed/resident reconstruction, FP16 Hadamard query/output transforms,
scale, GQA and bottom-right causal alignment are retained. `causal=False` also
survives metadata replacement. This preserves attention semantics; it does not
prove bitwise equality between differently shaped batched and serial launches.
No quantization policy, permanent-history flushing or resident-tail precision
changes here.

Native `kvarn_materialize_packed_kv_xe2` submits through
`c10::xpu::getCurrentXPUStream().queue()`. Ordinary FA's
`flash_api.cpp:varlen_fwd` obtains `vllmGetQueue`, whose `csrc/utils.h`
implementation returns the current XPU stream's queue. Triton and tensor
operations likewise use the active stream. Under the supported serial execution
contract, each materialize, FA consumption, output transform/copy, and subsequent
overwrite is ordered; persistent class/instance references keep scratch alive.
There is no per-request event or cross-stream ownership mechanism. Sharing by
geometry rather than stream therefore requires continued serialization in V2;
independent simultaneous target/draft streams would need isolation or explicit
dependencies. Such overlap is not qualified by this patch.

Host `.tolist()` reads, data-dependent looping and transient metadata make
this route unsuitable for graph capture. The released XPU guard explicitly
rejects graphs; the builder's broad `UNIFORM_BATCH` declaration and
`_verify_decode_path` capture-safe docstring do not prove DPAS overflow safety.
Keep eager qualification and the graph limitation explicit.

## Upstream alternatives and minimum residual

Neither frozen target contains KVarN operators. Semantic alternatives were
checked: `TurboQuantAttentionImpl` uses per-request continuation handling,
virtual decode rows for small queries and WorkspaceManager-backed dequantization
for larger continuations. Its slot representation, centroids and quantization
are different from KVarN group records/Sinkhorn/DPAS/resident pools. Its source
blob is unchanged across vLLM bases:
`8542e6164f0303a618194b45f4b7efd054a5a0a1`. This supplies design precedent,
not a compatible replacement. Upstream ordinary XPU `varlen_fwd` consumes
FP16/BF16/FP8 tensors; kernel change
`0b647c5717a382c6d7ea645571d3dbe8c7640696` generalizes block-size tiling,
not compressed history materialization.

**ADAPT and fold into v05** `fcab69494f1719e91e416aace17ef6ad501fe900`.
Retain the bounded serial fallback and regression contracts, with no separate
repair commit or enlarged scratch allocation. v10
`80d5166fcb0b7935f3f95b8d343e3e669940261f` supplies compact-width plumbing;
paired k08 `9bb1e2d428b8a25b262c0cd6704614bdf6ee3ad8` and k09
`f26ef2323399ab410299db5c8caec41c8d63215a` own
`_vllm_fa2_C.kvarn_materialize_packed_kv` and its `value_bits` ABI. v14 adds
no schema or kernel change; preserve both native and Triton materializers.

Upstream `5fe77aecfc7687c1f3cc49862022ce34d45d1784` removes legacy common
CPU-length fields. Adapt this helper to exact live lengths and active request
rows; V2's optimistic `seq_lens_cpu_upper_bound` cannot replace exact lengths.
Keep draft ownership/accepted-history repairs coordinated with v11
`73fb9e7aa230e9d6164c810a05175bd342995565` and v16
`2fdd9d71f6895379b0940a8f755b4c9095840558`.
DFlash2 additionally needs D128/Q32/KV8, noncausal window-2048 semantics and
context insertion before draft metadata construction. Passing `causal=False`
here supplies neither sliding-window masking nor that lifecycle. Preserve the
D256 target/MTP fallback while implementing compressed drafting separately.

## Observed and pending validation

Observed here: immutable patch/history, patch-ID, unchanged final files,
call/schema/queue inspection and upstream comparison. No tests, builds, GPU
work or services were run. Historical `docs/releases/xpu-v1.9.0.md` records
before/after reproduction, twelve bounded-scratch CPU cases within 603 installed
tests, GPU reconstruction/attention/canary/reuse checks, and at least 302,976
simultaneously occupied attention tokens after repair. These are recorded
old-stack results, not independently rerun snapshot qualification.

The CPU test covers fitting/overflowing ragged batches, causal/noncausal masks
and present/missing CPU lengths. The added XPU fixture compares capacities
385/260 against independent SDPA for both value widths, preserving cache and
canaries. Its `num_decodes=2` and padded record stride disqualify native
materialization: it exercises Triton fallback, and does not forbid ordinary
FA's reference fallback.

Pending: native-eligible overflow with dispatch assertions; scratch/temporary
lifetime tests on a nondefault current stream; invalid and zero-query boundaries;
exact V2 lengths under rejection/reordering; and long concurrent target/draft
requests with measured bounded memory. Requalify MTP/vision, DFlash window
semantics and matched performance on the complete pair. Existing historical
numerical failures remain evidence; this repair establishes no universal
lossless or performance claim.
