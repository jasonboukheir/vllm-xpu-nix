## Requirement and final released behavior

The feature implements compact quantized attention storage and native Xe2 execution needed for the retained Brutus/Arc Pro B70 profile. The released target uses W4A16 model weights with BF16 compute; the KVarN attention implementation rotates into FP16 working/tail tensors, stores packed history, and supports BF16 output after fused unrotation. These compute/storage roles must not be conflated.

The assigned commit adds 28 files/changes, including:

- Native normalized Hadamard transform, KV scatter and fused QKV transform/scatter. `kvarn_hadamard_scatter_xe2.cpp` supports FP16/BF16 inputs and stores FP16 tails; its two QKV entry points deliberately differ in allocator stream tracking.
- `kvarn_pack_balanced_kv_xe2` packs supplied Sinkhorn-balanced tensors into the frozen DPAS record layout. The native op is a writer; the caller's Triton implementation performs the balancing iterations.
- `KVarNFragmentLoader`, `KVarNDecodeFwdMainloop` and `KVarNDecodeD256G128DpasQ6PrefetchRecordCursorConfig` decode packed and resident FP16 pages within the same attention/softmax operation. The qualified native variant is numeric ID 18, with Q24/KV4, D256, G128 and K64 work units. Other decoder IDs fail closed.
- Cached-prefill materialization and independent dequantization support. Materialization follows a block table and per-request lengths while mixing packed pages and resident tails.
- Caller-owned split scratch, fused reduction/output Hadamard, optional BF16 output, and initialization of invalid LSE sentinels for empty row-local splits. `paged_decode_kernel.hpp` initializes sentinels only when the mainloop opts in. The ordinary `ChunkPrefillFwdMainloop` has `InitializeSplitScratchSentinels = false`.
- Q6-specific scalar output/reduction support in `DecodeFwdEpilogue`: the six-row tile cannot use the ordinary power-of-two block-store layout. The Q-row LSE ownership changes and zero-denominator guards are correctness behavior, not removable cosmetic refactoring.

The full released stack retains this feature. Kernel k09 (`f26ef2323399ab410299db5c8caec41c8d63215a`) adds `value_bits=2` throughout packing, readers, decode, dequantization and materialization. Its D256/G128 K4V2 record occupies 26,880 bytes per block/head versus 35,072 for compact K4V4. k10 (`c69cfad0586bb0eda4218fae495f446ae0e845bc`) changes the 16-split fused reducer; k11 (`2c39287deec5e59cc2656e6d4a6dce51a567c411`) adds aligned resident-page block loads with scalar fallbacks. They refine this implementation rather than superseding the feature.

Recorded release evidence establishes why retention matters: `docs/releases/xpu-v1.9.0.md` reports independent layout/attention checks, 603 installed tests, long-context/model qualification and 39–51% shorter unprofiled native K4V2 attention call spans for the later optimized candidate at 16K/65K. `docs/releases/xpu-v1.10.0.md` records all-K4V2 MTP2 qualification and 346,880 usable shared attention tokens under its 0.96 budget. These are historical released-stack results, not results for the new snapshot or DFlash2. k08 alone is not credited with the later k09–k11 speedup.

## Dead/stale paths and safe minimization opportunities

Two confirmed leftovers merit explicit treatment, but neither justifies dropping the native feature:

1. **Unused numerical scratch:** `legacy_max_logits` is never consumed by the native computation after its natural-LSE migration. `kvarn_decode_with_scratch_xe2` assigns `exp_sums` to `softmax_lse_accum`, while `max_logits` remains shape/device/alias validated and tracked solely for ABI compatibility (`kvarn_decode_xe2.cpp:319` onward). vLLM still allocates/views/passes the third scratch tensor in `_kvarn_native_scratch_views` and `_ensure_native_decode_scratch`. A coordinated schema/caller/test cleanup can remove it, but removing only the C++ validation or argument breaks the paired contract. This is a small allocation/maintenance reduction, not evidence of substantial serving headroom.
2. **Stale mixed-GRF explanation:** k08's CMake comment says the library contains selectable 128/256-GRF KVarN variants. Both k08 and the released tip only admit variant 18; searches find no `grf_size<128>` in the Xe2 attention subtree. The surviving decode/reducer launch properties explicitly select 256. Thus the stated 128-GRF experiment no longer exists. However, `MIXED_GRF_SIZE` also prevents a library-wide forced-256 flag from affecting helper kernels without explicit properties (writer/scatter/materializer). Its generated-code effect is not proven redundant. Correct the comment; remove the flag/helper option only after paired AOT code/GRF comparison and focused correctness/performance checks establish no retained benefit. Do not infer equivalence from the main decoder's property alone.

`kvarn_fragment_coords` and `kvarn_dequant` have no direct vLLM production callers in the searched released source, but are used by independent coordinate/record correctness tests and native diagnostics. They are not demonstrated dead code. Similarly, the allocating decoder, separate Hadamard and stream-tracked QKV entry points remain supported/reachable alongside optimized paths. No operator deletion is recommended without tracing and updating those users.

## DFlash2 extension boundaries

The existing native implementation does **not** implement the syvai checkpoint's D128/Q32/KV8, five noncausal sliding-attention layers with window 2048. It remains necessary for the D256 target and retained MTP profile.

- `kvarn_decode_xe2.cpp:15` hardcodes D256/G128/Q24/KV4, and validates those query/output/tail shapes. `KVarNDecodeD256G128Policy` and fragment-loader strides/swizzle formulas assume D256. The native API contains no window offset/mask argument and therefore cannot implement DFlash2 window semantics by changing dispatch eligibility.
- Materialization in that same file requires `[tokens,4,256]` outputs and `[slots,128,4,256]` tails. Native writer eligibility in vLLM `kvarn_attn.py:425` likewise requires D256/KV4, and its C++ writer encodes the matching record geometry. Scatter and standalone Hadamard check `[tokens,4,256]`, `[tokens,24,256]` and `[N,256]` respectively.
- `_resolve_kvarn_cache_layout` (`kvarn_attn.py:319`) accepts DPAS layout only for D256/G128/K4V4 or K4V2. Existing natural-layout/Triton code includes dimension and sliding-window parameters; it is a candidate route to investigate, not a qualified D128 compact implementation. All writer/reader byte offsets, record size, materializer and state-content accounting must agree before selecting it.
- The current K4V2 recent-FP16-history policy is a quantization-quality/residency policy. It is not the checkpoint's sliding-attention eviction/mask semantics. New windowed allocation, absolute-position mapping, block reuse and noncausal query masks must be tested independently. The backend's `supports_non_causal=True` documents a per-token verify path; it does not establish that narrow native qlen1 dispatch handles the new draft geometry.
- DFlash's out-of-forward context insertion requires vLLM to coordinate reservation, context write, query write, commit and reclaim. Native scatter reads the caller's slot/block indirection; it cannot repair builder ordering or ownership by itself. Preserve separate target/draft owners when extending V2.

A D128-specific native policy or verified natural-layout route may reuse parts of this feature. It must never reinterpret D256 records. Keep D256/MTP/vision regressions in the final matrix whichever route is chosen.
