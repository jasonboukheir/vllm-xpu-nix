## Requirement and effective old-stack behavior

The original commit message describes making narrowed attention builds compile without unsupported policy branches. Its actual implementation supplies a narrower and more precise property: **a wholly disabled Xe2 chunk-prefill policy never enters the recursive host boolean dispatcher**.

At the old upstream base, `csrc/xpu/attn/xe_2/chunk_prefill_utils.hpp::policy_dispatch_func` already checked both `is_chunk_policy_enabled<Policy>` and `is_chunk_policy_tuple_enabled<Policy, ...>` with `if constexpr` before calling the heavy `policy_dispatch_impl`. Disabled device implementations were already excluded. However, its five runtime booleans still recursively instantiated the host dispatcher for every policy referenced by `fmha_xe2.cpp`, reaching the checks only at the leaves.

k02 extracts the existing disabled-policy message into `report_chunk_policy_not_compiled`, adds `dispatch_enabled_chunk_policy<Policy>`, and changes all 12 standard/b16 call sites in `cutlass_chunk_prefill_impl` to use it. The wrapper's `if constexpr` returns the same diagnostic using runtime flags for disabled policies; enabled policies still use the original recursion and leaf tuple checks. The logical head-512 diagnostic remains 512 for both policy families. The namespace and hidden visibility remain intact.

This reduces host template expansion for a selective build; it does not add device coverage, change enabled attention arithmetic, or select a new runtime attention algorithm. Both touched files are byte-identical between k02 and the full released kernel tip: none of k03–k11 repairs, reverts, or supersedes this behavior.

The released Brutus/Intel Arc Pro B70 profile is a concrete consumer. At packaging baseline `4ac4375...`, `flake.nix::kvarnValidationKernelConfig` contains three prefill tuples:

```text
96,false,false,false,false,false
256,true,true,false,false,false
256,false,true,false,false,false
```

These generate four enabled policies (standard/b16 for D96 and D256) and leave eight disabled. The target generator still enables both policy families per listed head size. By source-level counting, an unguarded disabled policy produces 31 recursive dispatcher specializations plus 32 leaf specializations; k02 bypasses those 63 specializations in favor of one wrapper. Thus the old narrow profile avoids 504 host dispatcher specializations for its eight disabled policies. This count describes the template call tree, **not measured compiler memory, emitted object size, or elapsed-time savings**. Adding D128 coverage for issue17 would reduce the number of disabled policies; it does not eliminate the distinction.

The inspected target `chunk_prefill_default.conf` already includes all six head sizes, so both default and full presets enable all 12 policies. k02 provides no disabled-policy-tree pruning for either preset. Tests of those presets are controls, not evidence of the narrow-profile benefit.

## Dependencies and minimum residual

- k01 is the parent by history, not a semantic prerequisite: its oneDNN change is unrelated. No later kernel patch uses either new helper by name or changes either touched file. k02 should remain an independently explained build optimization, rather than folding into KVarN arithmetic.
- No registered operator, public schema, tensor format, Python signature, or cross-repository ABI is added or removed. vLLM requires no paired code deletion if a measured decision later drops this optimization. The dependency is the packaging build configuration: the benefit requires disabling entire policies through `VLLM_CHUNK_PREFILL_CONFIG`.
- Minimum residual is the existing early policy gate, shared diagnostic, and 12 call-site substitutions. Preserve upstream's extern declarations, tuple gating, per-variant generation, namespace isolation, and generalized b16 selection. There is no need to restore the historical packaging dispatcher-splitting patches `0007`/`0008` or add a new build option.
- Correct the rationale when producing the reconciled commit/report: the source proves early **host-dispatch pruning**, not an otherwise unsupported device-kernel instantiation. `docs/build.md` currently links this fix to tens-of-GiB dispatcher memory; that attribution needs the comparison below before being repeated as a measured causal claim.
- If a cold comparison demonstrates no failure or worthwhile residual benefit, DROP k02 with that evidence and update the build documentation. That would be retirement of an immaterial optimization, not semantic replacement by `5e5161e`.
