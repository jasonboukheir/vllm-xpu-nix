## Requirement and behavior in the final old stack

v06 enables local retained prefix reuse for the Qwen `qwen3_5` model family
with BF16 compute, compact K4V2, TP1/PP1 and eager V1 execution. It removes the
independent-pool rejection of prefix caching while retaining rejection of KV
events. Pool-qualified cache lookup and ownership supplied by v05 remain
prerequisites. An overlapping integer block ID in another physical pool must
never constitute a hit or acquire the wrong reference count.

The old aligned EAGLE/MTP lookup capped an identical resend at `P - 1`, then
dropped another attention block. For P=128 and B=32, a resend hit 64 while a
longer sibling hit 96. Retaining a hash for 64 did not materialize recurrent
state there. v06 therefore split the real scheduler at both 64 and 96, fixing
first-resend misses that manual per-block test allocation had hidden.

The independent allocator also adds at most `max_num_seqs` idle recurrent
checkpoints per align-mode Mamba pool, using only memory remaining after live
recurrent reservations and one full `max_model_len` attention allocation.
This avoids an otherwise observed miss in a four-request repeated batch while
preserving the 262144-token limit. It is a capacity/performance requirement,
distinct from a worker's per-request prefill checkpoint allocation.

Later v07 `a76fbb1ce06d50159978786f70daf44c27847ddd` preserves these
capabilities but changes the default deployment policy: `active_only` releases
idle GPU hashes, and `_uses_independent_cpu_offload` suppresses the extra
recurrent reserve for `OffloadingConnector` + `IndependentCPUOffloadingSpec`.
The predicate is based on the connector/spec, not a direct `gpu_cache_policy`
comparison. Do not describe or replay it as a policy-string check. The final
v1.12.2 manifest records this RAM configuration and zero extra retained GPU
checkpoints. Retained GPU caching without this connector remains supported.

v08 `dcba4007ef6af8ba143d2794c194c36b58397339` repairs incomplete MTP
pages at the context ceiling and padded rows in KVarN. It does not remove the
prefix capability or capacity logic. Its page-completeness requirement must
hold for the new V2/DFlash lifecycle before any retained/RAM hit is published.

## Upstream coverage and minimum residual change

### Aligned resend: upstream supersedes the extra scheduler stop

`d8fa463e2ba751759a3534dd3ce11af92f1eed83` changes the actual producer,
lookup and worker alignment contract, not merely a similar test:

- Frozen `vllm/v1/kv_cache_interface.py:1110`,
  `get_mamba_prefill_checkpoint_position`, uses `P` as the proof limit under
  EAGLE and `P - 1` otherwise, then applies the EAGLE drop once.
- Frozen `vllm/v1/core/kv_cache_coordinator.py:873` and `:950` allow attention
  to inspect the extra proof region using `eagle_proof_margin`, bounded by
  available hashes. This fixes both reconciliation and shared-prefix lookup.
- Frozen `vllm/v1/core/sched/scheduler.py:443`,
  `_mamba_block_aligned_split`, uses the common checkpoint helper and can
  avoid a stop when the backend materializes a valid internal checkpoint.
- `partial_hash_hits_enabled` and `resolve_cache_hit_alignment_tokens` in
  `kv_cache_utils.py:750` and `:909` propagate the actual coordinator hit grid.
  `KVCacheConfig.hash_block_size` and `cache_hit_alignment_tokens` carry that
  contract to workers; `MambaManager` uses it for checkpoint reservation and
  publication.
- The same upstream commit changes
  `test_hybrid_mamba_retention_mtp_resend_of_aligned_prompt` to require
  **96-token hits for both resend and extension**, explicitly retiring the
  old expectation of 64 for the resend.

Therefore remove v06's standalone `resend_cache_position` arithmetic and its
extra scheduler stop. Retain the newer upstream helper, proof margins and
alignment propagation when rebasing the local independent-pool coordinator.
For the no-internal-checkpoint P=128/B=32 test, the frozen scheduler's source
now yields chunks ending at 96 and 128; the extra chunk ending at 64 is
unnecessary. Keep the local improvement of driving the real splitter and
parameterizing shared versus independent pools, but update its expected hit
and state assertions. Do not require a 64-token state that the scheduler no
longer needs to produce. This expected trace is source-derived here, not a
new runtime test result.

Preserve `7e583e615c20ee4ff0cd82aac592c7d6310aa7c3`'s `prefill_end`
reservation parameter, `d882bddbeab6b4a0d5861dfcb171bf61ce2109d6`'s
prompt-end sparse-retention handling, and
`6fa67afed999d7cbab6a9a7492b2538dd8c2aff0`'s stale speculative-block
retirement. These are upstream worker/admission correctness improvements;
they do not supply independent physical pools or spare idle capacity.
Coordinate scheduler alignment with v02 rather than replacing its separate
GDN correctness behavior while removing this one redundant stop.

### Independent-pool caching and spare recurrent capacity: retain/adapt

The target has no KVarN or `KVCachePoolSpec` implementation. Its shared-pool
checkpoint fixes do not provide the pool-qualified cache ownership, explicit
KVarN capability allowance or independently budgeted recurrent reserve.
Retain v06's removal of the prefix-cache prohibition in `KVCacheManager`,
preserve KV-event rejection, and retain the positive/negative capability
checks with the narrow V2/DFlash support established by the feature port.
Removing the V1 guard alone is insufficient evidence of that support.

Retain the spare-checkpoint algorithm only after v07's suppression condition.
Adapt its byte accounting to v0.32's packed layout/stride planner and final
speculative/Mamba specs, as assigned to v05. Do not hard-code the old four
checkpoints or 263040 attention-token allocation; they are outcomes of the
old profile. A wider DFlash verifier and its draft pool can change the live
reservation and available attention capacity.
