# v08 — ADAPT: consistent recurrent reservation in capacity planning

Audit owner: `/root/audit_v08`; read-only investigation, 2026-09-20. Only this
report was written. Source instructions, commit-audit contract, issue snapshot,
manifest, inventory, compatibility/port maps and v05/v07 reports were read.

## Frozen inputs and requirement

Assigned commit `3b6c822e8a4f56dc3904c7fce388a76dff4c7bdd`, parent
`2352837c5eb1e98113c88e5158363c98e14fa5a5`, patch ID
`f3b6136899fbe171d14864d84344ebac6f119ff8`. The final released vLLM tree is
`2fdd9d71f6895379b0940a8f755b4c9095840558`. The frozen upstream targets are
vLLM `e378275a8f20eac9e92212e4a1fee84ec5a31dc7` and kernels
`da16a5595c105605bcd44b558c7933b934a05f85`; old bases, both fork tips and the
complete paired inventory remain authoritative in [manifest.json](../manifest.json)
and [commit-map.json](../commit-map.json).

The KVarN independent-pool allocator reserved recurrent state for every
`scheduler_config.max_num_seqs` slot, then assigned remaining memory to
attention. Before v08, `_max_memory_usage_bytes_from_groups` charged only one
request's recurrent state. Consequently admission could approve a context
length that allocation rejected, and `_estimate_max_model_len_from_groups`
could recommend an impossible maximum. This is a capacity correctness repair,
not a kernel speed optimization.

v08 changes the estimator to multiply only Mamba demand by runner slots; one
full-context request's attention demand remains the admission minimum. Its
`bytes_per_group_block` rename separates the independent-pool list from the
shared-pool scalar and fixes a reported type-check failure without changing
allocation behavior. Tests cover one/four slots and `none`/`align` cache modes,
restoration of `max_model_len`, actual pool allocation and failure one attention
page beyond the estimated capacity.

The historical B70 workload was W4A16/BF16 Qwen3.8-27B, four slots, MTP2,
2,048 prefill tokens and two images. The final release extends this to K4V2
target and draft caches. Its per-request 262,144-token ceiling is distinct from
the shared attention capacity. V2 and syvai DFlash2 increase the importance of
honest capacity accounting; v08 alone implements neither integration.

## Final-old behavior and upstream coverage

Release-only v13 `d6cb2e6cb2de2321fd28eea6e0aada93fb8bd736` repairs another
entry into the same accounting problem. With an independent-pool
`num_gpu_blocks_override`, earlier code multiplied one-request attention and
recurrent bytes together. A one-request override therefore underfunded four
recurrent slots. v13 introduces `_independent_pool_bytes_for_requests`: the
override multiplies attention demand only, recurrent demand still uses
`max_num_seqs`, and `_null_block_bytes` adds one null block per physical pool.
v08's estimator remains intact through the final release, duplicating the
one-request case of this later helper. v13 complements rather than supersedes
the requirement.

At the frozen vLLM target, `vllm/v1/core/kv_cache_utils.py` still implements
ordinary device groups using a shared allocation/block count.
`_max_memory_usage_bytes_from_groups` computes shared-pool one-request demand;
`get_kv_cache_configs` converts an override into ordinary block bytes. There
is no KVarN branch. This is not evidence that ordinary upstream allocation is
incorrect: it does not make the fork's separate all-slot recurrent reservation.

Upstream `d43bb2f37f87a63d3a9a299c97050443cf6a2520` adds HiSparse allocation;
`e19a3e172ecc1d1ece8ecce9dfd91bf811a814a0` shares its host cache across TP ranks.
Target `hisparse/layout.py:get_hisparse_gpu_memory_usage` and
`get_hisparse_kv_cache_config` split sparse-MLA host/device storage, while
`_estimate_max_model_len_from_groups` can probe that allocator directly.
These are useful alternate planning mechanisms, but do not implement independent
device attention/Mamba reservations. Preserve their branches during the port.
TurboQuant's `customize_spec` supplies `slot_size_aligned` for its own cache
format; it does not replace KVarN's representation or recurrent pool policy.

Upstream `f730a93d2bf2cad3002578238d5a1035ee1f4177` adds
`max_num_active_seqs`. Target `config/scheduler.py` explicitly distinguishes
RUNNING admission from runner capacity. `core/sched/scheduler.py` uses
`max_num_active_reqs` in its waiting-queue admission loop, while
`worker/gpu/model_runner.py:GPUModelRunner.__init__` still sizes
`max_num_reqs` from `max_num_seqs`. Retain recurrent reservations against
`max_num_seqs` consistently in estimation, overrides and allocation. Substituting
the optional lower active cap only in the estimator recreates v08's mismatch;
changing the allocator policy too would require separate lifecycle evidence.

Target `kv_cache_interface.py:MambaSpec.max_memory_usage_bytes` remains the
per-request authority: `none` includes speculative states; `align` also
includes checkpoint blocks; `all` depends on context length. Preserve this
calculation rather than hardcoding MTP2's three states. The selected kernel
tree has no KVarN or scheduler-slot capacity implementation and supplies no
semantic replacement for this Python-side planning.

## Disposition, residual and dependencies

**ADAPT, folded into the owning KVarN pool feature v05
`fcab69494f1719e91e416aace17ef6ad501fe900`, together with v13.** Use one
accounting helper for the minimum reservation: layer count × physical page
bytes × per-request resident blocks, multiplied by runner slots for Mamba and
the requested attention-capacity count otherwise. Admission/auto-fit use
attention count one; overrides use their requested count. Keep null accounting
separate and exactly once. Allocation and estimates must consume the same
reservation policy. The variable rename needs no separate repair commit.

v07's parent SHA above owns concurrent admission. v12
`6519bf709dbb354926f1ac3908e2c7917e9abd23` changes independent grouping for
mixed target/draft precision; size actual groups and layer counts. Native
KVarN k08 `9bb1e2d428b8a25b262c0cd6704614bdf6ee3ad8` and compact K4V2 k09
`f26ef2323399ab410299db5c8caec41c8d63215a` remain paired feature dependencies,
but v08 adds no operator/schema/ABI change. Ownership and bounded-materialization
repairs v11/v14 remain independently necessary; capacity admission cannot
replace them.

For DFlash2, extend this policy to its bounded draft window and actual page
geometry rather than forcing every attention group to reserve full target
history. Charge weights, context projection, tails and scratch through measured
available memory; report usable target tokens separately from draft tokens.

call paths, plus historical raw artifacts. No new pytest, GPU, build or service
