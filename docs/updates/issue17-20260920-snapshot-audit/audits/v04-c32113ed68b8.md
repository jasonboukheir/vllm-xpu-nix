# v04 — ADAPT: preserve the XPU residual RMSNorm requirement

**Disposition: ADAPT.** Keep the functional, row-local residual RMSNorm on
the XPU paths that need it. CUDA already has a native batch-invariant launch
policy, so the global replacement and replacement of native CUDA regression
coverage are broader than the demonstrated residual gap. Restore upstream
native coverage and add effective XPU coverage. Do not drop the XPU helper or
replace it with a native launch tweak before validating its numerical and
aliasing contracts, including the v05 Gemma caller.

Audit owner: `/root/audit_v04`; read-only investigation on 2026-09-20.
Only this report was written. No source/ref changes, GPU execution, service
operations, builds, or publication were performed.

## Requirement and effective released contribution

`vllm/model_executor/determinism/batch_invariant.py` originally routed
`rms_norm_batch_invariant(..., residual=...)` directly through
`ops.fused_add_rms_norm`, mutating both inputs. v04 supplies
`_fused_add_rms_norm_kernel`: one Triton program per row, fixed 1,024-element
reduction blocks, FP32 residual addition and square accumulation, and separate
normalized/residual outputs. Batch size changes the grid, not the per-row
reduction tree. Weight is optional; a provided weight is made contiguous.
Inputs are flattened/contiguous internally and restored to their original
shape in the outputs. The input tensors themselves remain unchanged.

This is a reproducibility and functional-result requirement, not a demonstrated
speed improvement. Its intended observable property is exact equality for the
same row and residual when unrelated rows are added to a batch. It also changes
numerics: normalization uses the unrounded FP32 sum, while the returned residual
is rounded to input dtype. The native XPU vectorized path instead stores its
low-precision sum and normalizes from that rounded value. A replacement must
not treat those algorithms as interchangeable merely because their launches
are deterministic.

The generic caller is `RMSNorm.forward_cuda` (also used by `forward_xpu`) when
`VLLM_BATCH_INVARIANT` is enabled. Upstream documents Intel XPU/Triton support
and requires Triton Attention for its complete XPU batch-invariant mode; this
local normalization fix alone establishes no full-model guarantee.

Later v05 `fcab69494f1719e91e416aace17ef6ad501fe900` adds an independent XPU
caller in `GemmaRMSNorm.forward_native`. It forms `weight.float() + 1.0` and
passes a `request_invariant_apply_once` callback to
`request_stable_linear.py:apply_rms_norm_by_request`. When supplied, that
callback processes the whole packed tensor with this helper before the
canonical M64 slicing fallback. `GemmaRMSNorm.forward_xpu` explicitly bypasses
the fused native Gemma kernel when the qualified request-stability policy and
request slices are present. Removing v04 would therefore change residual
rounding, input mutation, launch behavior, and mixed FP32-weight/BF16-input
handling for this caller.

The v05 selector is explicitly the AEON model
`jasonboukheir/Qwen3.8-27B-AEON-Ultimate-Uncensored-BF16-W4A16-AutoRound`,
revision `6b0622f4354481d5d04577d48ba0db844efc1330`, BF16 compressed-tensors,
compact K4V4/K4V2, eager V1, language-only, no speculation/prefix caching,
and restricted parallelism. It is inactive for the released RedHat
K4V2/MTP2/vision configuration on Arc Pro B70 and the requested syvai V2
DFlash2 configuration. That inactivity does not retire its requirement.

`git diff --exit-code c32113ed... 2fdd9d71...` for both files changed by v04
passes with no differences. The path history contains only v04. Thus no later
local main or release-only commit repairs, reverts, or supersedes its code.

## Minimum residual, dependencies, and folds

1. Retain v04's XPU functional fixed-tree implementation and weight/shape
   handling. Preserve its direct use by the qualified v05 Gemma path, even
   when global `VLLM_BATCH_INVARIANT` is unset. The selector and v04 cannot be
   reconciled independently by deleting one half.
2. Narrow the residual replacement to XPU while retaining upstream's native
   non-XPU route under its existing contract. No non-XPU fork-specific caller
   was found beyond generic `RMSNorm`; the Gemma callback is XPU-policy gated.
   Keep XPU outputs functional. Restoring CUDA behavior needs its original
   native tests plus a dispatch regression; do not claim the optional global
   helper is now functional across platforms.
3. Restore upstream's direct native residual regression instead of replacing
   it with helper coverage. Add XPU helper/reference/invariance/aliasing cases
   in the existing suite and select an XPU-capable skip marker. Fold these
   tests and the scope adjustment into the surviving v04 commit.
4. A smaller XPU native fixed-launch implementation is a reasonable future
   comparison, not an established substitute. It must address optional and
   FP32 Gemma weights, residual rounding, output allocation/mutation, strides,
   and effective selector policy together. No native API/schema change is
   required merely to retain v04.

v04 has no source prerequisite on v03 despite its parent relationship.
v05 depends on it for the scoped Gemma callback. k01
`8530de9d4298b199436079c46233acb33efb6fc2` makes W4A16 matmul repeatable;
GEMM determinism does not imply normalization batch invariance and is not a
replacement. No repair commit needs folding from the original inventory.
Keep this small independent fix reviewable; if the AEON request-stability
portion of v05 is split into its own feature, explicitly record its v04
dependency. The DFlash fixes remain upstream-covered independent behavior.

## Validation: observed versus pending

Observed during this audit:

- Verified assigned parent/patch content and stable patch ID; verified CUDA
  #48391 ancestry; inspected exact old/base/target/released call paths and
  native dispatcher differences; verified unchanged v04 files through the
  complete released stack. These are source checks, not runtime validation.
- Existing v04 residual regression covers H512/H4096, FP16/BF16, batch sizes
  1 versus 4/300, and 16 seeds. It checks exact output/residual row equality
  and a reference tolerance. **Its `@skip_if_not_cuda` marker excludes XPU**,
  as confirmed by `tests/v1/determinism/utils.py`. Simply running the existing
  test file on Brutus can therefore report skips instead of testing this fix.
- Historical `benchmark-results/kvarn/20260831T010620Z/final-acceptance.json`
  records AEON request-stability service success, including C4, cancellation,
  127+258 and 65023+512 boundaries, and fresh-process identity. Its provenance
  is vLLM `5acf37c1f7043e282bb447a63da20792f81d4fe1`, kernels
  `8f52482baa7c23ae976c11b1c1c88e3db4a25867`. Inspecting that vLLM object shows
  it still had the native residual branch: these results **do not validate
  v04**, nor establish that the fixed-tree kernel caused the observed success.
  They are historical evidence for the caller's required behavior only.
- `xpu-v1.10.0` qualifies RedHat K4V2/MTP2/vision, where the AEON selector is
  inactive. Its serving results do not isolate this normalization fix. No
  matched v04 latency/allocation benchmark or exact-pair GPU regression was
  found in the bounded artifact search.

Required before final qualification:

- On the actual loaded XPU package, compare upstream alone, retained helper,
  and any proposed native/IR replacement for the same rows at 1, 4, 255, 256,
  257, and 300 tokens, including H4096 and production hidden sizes. Vary
  alignment/strided views and batch placement. Require exact replay and
  cross-batch equality for the helper's output and returned residual.
- Test input preservation and output non-aliasing explicitly; test weight=None,
  noncontiguous inputs/weights, multi-dimensional flattening, BF16/FP16 and
  BF16 activation with FP32 `weight + 1` Gemma semantics. Compare normalized
  results against an FP32-add FP32-reduction reference. The existing test
  references `x + residual` rounded to activation dtype and uses loose BF16
  tolerance, so it does not tightly specify the new arithmetic contract.
- Exercise the retained AEON policy's model-level isolated/concurrent/mixed
  scheduling trajectories and verify the helper actually executes. Separately
  verify it stays inactive for the new RedHat/syvai V2 profile unless a new
  supported policy is deliberately introduced. Do not infer complete model
  batch invariance from this operator test.
- Measure warmed latency and allocation overhead at decode/prefill sizes if
  choosing between implementations. v04 allocates two outputs and may copy
  noncontiguous inputs; no speed claim is currently supported. Preserve
  upstream CUDA native regression coverage for the narrowed scope.
- Independently qualify DFlash stacked weights using distinct per-layer
  values against the actual loaded library. That check neither validates nor
  obsoletes residual RMSNorm.
