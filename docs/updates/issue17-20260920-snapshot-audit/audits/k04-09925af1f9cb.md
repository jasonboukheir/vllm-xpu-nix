## Requirement in the final old stack

Qwen GDN prefill on Xe2/Arc Pro B70 must produce repeatable output and recurrent state, independent of scratch/cache reuse and request batching. The service-shaped geometry is BF16, K16/V48, D128, TP1, convolution width four, and 64-token native chunks. This is a correctness requirement, not an optimization.

k04 changes two barrier sites and adds 780 test lines: fresh-state replay at 63/64/65/104/107/162 tokens; ragged batch separation; 4095-token canonical state carry; and a 24-call asynchronous T107 chain including quantized projections and allocator churn. Replay requires exact equality; longer fresh-state cases also compare against the reference at 5e-2 tolerance.

The released header has exactly k04's blob `06fd1512cd01be6bf7da8e287b4d047f6714a9a3`. Later k05 adds a mixed-decode test without altering these tests or barriers. KVarN and speculative rollback changes do not supersede this prefill behavior.

## Upstream coverage and synchronization proof

The old upstream and target header share blob `b457f3d06213cf141dfed99d0ed1a6a4b387dc7f`. The sole intervening GDN commit, `da16a5595c105605bcd44b558c7933b934a05f85` (#600), changes speculative convolution/recurrence traversal to `query_start_loc` ranges and relaxes the speculative-capacity assertion. It changes neither `chunk_fwd_o_kernel` nor its launch ownership.

Earlier upstream fixes are material:

- `c9989668e7f280747680def85d58d116126c2249` (#411) inserts the barrier before each chunk's SLM refill.
- `619c409849500e0f56f8da00d5f11c4aa75cd6f9` (#560), already an ancestor of the old base, replaces local-only barriers with `sycl::group_barrier`, including the U producer/consumer and next-chunk barriers.

Group barriers include memory ordering, not merely work-item arrival. The [Khronos reference](https://github.khronos.org/SYCL_Reference/iface/group-functions.html#sycl-group-barrier) specifies release/acquire synchronization. Installed oneAPI `2026.0.1.27` headers corroborate this: `sycl/group_barrier.hpp` calls `ControlBarrier` with sequential consistency; `sycl/detail/spirv.hpp:1244` includes `CrossWorkgroupMemory` as well as local-memory semantics. Therefore k04's substitution of `item.barrier(global_space)` for the existing U `group_barrier` adds no missing global-memory guarantee. A compiler defect would require separate evidence.

At the frozen target, `kernel_launcher` launches `global_fwd_o(batch_size,num_v_heads,1)`. Each work-group owns one request/value-head and processes its chunks and dv tiles sequentially; its eight subgroups use `chunk_gemm_policy_64x64x32_4x2`.

1. **U and stateful O2:** the barrier at approximately line 1160 follows all O2 and current-dv U stores before `gemm_TTS(O2_tensor,U_tensor_T,...)`. Keep that upstream barrier.
2. **Next-chunk S:** S stores finish before each subgroup enters the next iteration's existing barrier around line 985. Subsequent S reads occur after it. The added end-of-chunk barrier is redundant for this handoff; final state visibility belongs to kernel/stream ordering.
3. **Fresh-state O2:** subgroups store their O2 tiles with `copy(copy_O2_c,...)`, skip the entire `has_prev_state` branch, then read O2 in the final output GEMM. The intervening S computation contains no work-group synchronization. Different subgroup-owned O2 tiles are consumed by the matrix product, so a producer/consumer ordering edge is missing. k04's new barrier supplies it.

Minimum residual: leave the U barrier unchanged and put one `sycl::group_barrier(item.get_group())` at the start of `if (!has_prev_state)`, before its output dv loop. That predicate is uniform within the work-group. Preserve existing SLM barriers. This removes the unconditional per-chunk barrier while retaining the uncovered fresh-state ordering.

[Open PR #523](https://github.com/vllm-project/vllm-xpu-kernels/pull/523) is an alternate optimization, outside the target. Its dv-grid split is identified as `8951252f4b29beaad77ee833de3d1db6ff245996`; its public review flags shared O2 writes between work-groups. That commit was unavailable locally and its patch could not be retrieved, so this audit does not qualify its implementation. Any future adoption requires ownership analysis: this work-group barrier cannot fix a cross-work-group race.
