[commit-map.json](../commit-map.json).

The independent KVarN allocator reserves recurrent state for every
`scheduler_config.max_num_seqs` slot before assigning remaining memory to
attention. Before v08, admission and context auto-fit charged only one request's
recurrent state. Consequently the estimated context could pass admission but
fail allocation. v08 multiplies only recurrent demand by the configured slots;
attention admission still funds one maximum-context request. It also gives the
per-group block-byte list a distinct name, avoiding a scalar/list type clash.

This is capacity correctness, not a kernel speed optimization. The supported
release workload remains Brutus/B70, the RedHat Qwen3.8-27B W4A16 target,
BF16 compute, eager V1, K4V2 target/draft caches, bundled MTP2, vision, four
scheduler slots and a 262,144-token per-request ceiling. That ceiling differs
from total shared usable attention capacity. This audit does not extend the
profile to V2 or DFlash.

## Exact target coverage and later repairs

At `ced6857`, `vllm/v1/core/kv_cache_utils.py` has no KVarN allocation branch.
`get_kv_cache_config_from_groups` (line 1648) uses ordinary shared-device
allocation outside its special layouts. `_max_memory_usage_bytes_from_groups`
(line 2405) calculates a shared block-byte cost multiplied by the sum of
per-group request blocks. `_estimate_max_model_len_from_groups` (line 2464)
uses that estimate except for HiSparse, and `get_kv_cache_configs` (line 2617)
translates ordinary overrides into physical block bytes. These paths do not
implement the fork's independently sized attention and all-slot recurrent
pools. This does not identify a bug in upstream's different shared-pool policy.

Upstream `d43bb2f37f87a63d3a9a299c97050443cf6a2520` adds HiSparse and
`e19a3e172ecc1d1ece8ecce9dfd91bf811a814a0` shares its host cache across TP
ranks. The target's `hisparse/layout.py:get_hisparse_gpu_memory_usage` and
`get_hisparse_kv_cache_config` size host-backed sparse-MLA storage, and auto-fit
can probe that allocation. Preserve those dispatches and per-worker handling;
they are not an alternative implementation of the KVarN/Mamba reservation.
Upstream `d29c88f162a3ec17ddb0afdf5f4f3b3ca6b84d59` adjusts sliding-window
primary block sizing; it also does not supply independent recurrent pools.

The exact release's V1 `worker/gpu_model_runner.py:GPUModelRunner.__init__`
sets `max_num_reqs = scheduler_config.max_num_seqs` (line 551).
`config/scheduler.py` has no `max_num_active_seqs` field. The later snapshot
commit `f730a93d2bf2cad3002578238d5a1035ee1f4177` is **not** an ancestor of
`ced6857` (`git merge-base --is-ancestor` returned 1). Do not copy that
snapshot-specific test or configuration advice from the paused audit.

`kv_cache_interface.py:MambaSpec.max_memory_usage_bytes` (line 1034) remains
the per-request authority. Its AST is identical between the old base and the
selected release: `none` includes speculative states, `align` also includes
prefill checkpoint blocks, and `all` depends on context length. Preserve this
calculation instead of hardcoding MTP2's three recurrent blocks. This Python
reservation requirement has no replacement in the companion kernel release.

Release-only v13 `d6cb2e6cb2de2321fd28eea6e0aada93fb8bd736` fixes the same
reservation policy at the attention-capacity override entry point. Its helper
`_independent_pool_bytes_for_requests` scales recurrent groups by runner slots
and other groups by requested attention capacity; `_null_block_bytes` charges
one null block per physical pool. v08's estimator duplicates the one-request
case of this helper. The repairs complement each other. The allocator file is
byte-identical from v13 through the released tip; later test expansion does
not supersede the behavior.

## Disposition and minimum residual

**ADAPT; fold into v05 `fcab69494f1719e91e416aace17ef6ad501fe900` with
v13.** Preserve the existing behavior while porting the owning independent-pool
feature. Consolidate the duplicated admission/auto-fit arithmetic with v13's
helper, passing attention-request count one. Its group cost is actual layer
count × physical page bytes × per-request resident pages, multiplied by
`max_num_seqs` for Mamba or the requested attention capacity otherwise.
Allocation must use the same policy. Add/subtract null storage exactly once
and retain the distinct per-group byte-list name where needed.

Retain v07's concurrent-admission requirement
`2352837c5eb1e98113c88e5158363c98e14fa5a5` and v12's actual group/layer
geometry `6519bf709dbb354926f1ac3908e2c7917e9abd23`. Paired native feature
dependencies remain k08 `9bb1e2d428b8a25b262c0cd6704614bdf6ee3ad8` and
K4V2 k09 `f26ef2323399ab410299db5c8caec41c8d63215a`. v08 adds no native
operator, schema or ABI. Cache ownership and reset correctness remain separate
feature requirements; accurate capacity does not establish them.
