## Requirement and effective old stack

This commit supplies 31 files of native grouped K4V4/K4V2 writers/readers,
Hadamard transforms, K/V and Q/K/V scatter, bounded materialization, and
attention over packed history plus resident FP16 tails. D256/G128 compact
records occupy 35,072 bytes per KV head for K4V4 and 26,880 for K4V2. The
associated vLLM backend depends on these record layouts, mutable tail pools,
and physical-block-to-resident-slot indirection. Removing the feature would
remove the native compact-cache implementation; full-cache materialization
would not preserve its bandwidth and memory behavior.

The stable xpu-v1.12.2 profile in `docs/releases/xpu-v1.12.2.json` uses
`RedHatAI/Qwen3.8-27B-INT4` at
`bf08f3dbd9a324e53956920aad378a1f1b6dd24a`, W4A16 weights, BF16 compute,
eager V1, compact K4V2 target and MTP2 caches, 262144 context, four scheduler
slots, 2048 batched tokens, prefix caching, and an 8 GiB bounded CPU arena
with `gpu_cache_policy=active_only`. Previous qualification identifies the
Brutus hardware as Intel Arc Pro B70. The current user scope retains compact
target storage and RAM prefix behavior while migrating to V2/DFlash2.

k07 is the final kernel commit; no later kernel repair/revert changes it.
The later paired vLLM commits `81dc387cf9a8`, `a76fbb1ce06d`, and
`dcba4007ef6a` add retained prefixes, host offload, and context-ceiling
completeness without changing this native ABI. xpu-v1.12.2 explicitly records
the native kernel source and derivation as unchanged from xpu-v1.12.1.

## Upstream coverage and minimum retained delta

There is no kernel old-to-new delta: both bases are exactly `ddf336d86e3c`.
The vLLM target's `requirements/xpu.txt:23` pins
`vllm_xpu_kernels==0.1.15.4`; its Torch pin is 2.14.0. A recursive search of
kernel-target `csrc`, `tests`, and `vllm_xpu_kernels` finds no `kvarn` or
`k4v2`. The corresponding search of vLLM-target `vllm` and `tests` is also
empty. This is absence evidence combined with inspection of alternate paths:

- Kernel `flash_api.cpp::mha_varlen_fwd`/`varlen_fwd` accepts ordinary K/V
  tensors and scales. It lacks the packed grouped records and resident-slot
  mapping consumed by KVarN. Ordinary FP8 support cannot decode these K4/V2
  fields, grouped scales, zero points, and DPAS swizzles.
- vLLM `turboquant_attn.py::customize_spec` allocates per-token/head slots
  through `state_content_bytes`; its declared layout is `LBNHC`, and it uses
  TurboQuant-specific store/decode routines. `ultraquant_attn.py` specializes
  that backend for FP4/UE8M0 slots. Neither supplies KVarN record compatibility
  or the custom resident-tail/host-offload lifecycle. Replacing the user’s
  cache with either would require separate quality, capacity, and performance
  evidence and is not a demonstrated reduction of this patch.
- V2's generic attention interface remains tensor-based, so the native
  operators themselves do not depend on V1 runner classes. New runner and
  draft metadata paths are not replacements for the operators.

Retain the full effective feature, including `flash_api.cpp` schemas, five
public Xe2 headers, writer/scatter/Hadamard/materializer sources, the native
decode mainloop and reducers, shared epilogue corrections, and ordinary
attention opt-out of KVarN scratch-sentinel initialization. Keep tests and
independent byte/numeric oracles. Preserve mixed-GRF/CMake integration and
the `subtiles` spelling allowance; this commit does not own the Torch pin.
There is no evidenced upstream-driven native deletion for this release.

## Paired ABI and V2/DFlash2 viability

At `dbb684f`, `csrc/flash_attn/flash_api.cpp:458-529` registers:
`kvarn_fragment_coords`, allocating/reusable-scratch decode,
`kvarn_materialize_packed_kv`, `kvarn_dequant`, Hadamard K/V scatter, both
Q/K/V scatter lifetime variants, balanced packing, and Hadamard transform.
Keep argument order/defaults for `dpas_layout`, `value_bits`, split count,
kernel variant, unrotation, and BF16 output. The paired checks in
`dcba4007:vllm/v1/attention/ops/triton_kvarn_decode.py:333-382` inspect those
installed schema arguments before selecting native paths.

`kvarn_decode_xe2.cpp::kvarn_decode_with_scratch_xe2` requires FP16
`query[B,24,256]`, `1 <= B <= 12`, four KV heads, G128 FP16 tails, byte
records, int32 block tables/sequence lengths/lookup, DPAS layout, and variant
18. K4V2/K4V4 are both supported. Sequence lengths are per-query row; the
native mainloop uses `CausalMask=false` and bounds each row through its
sequence length. It has no runner-specific request or rollback semantics.
Scratch shape must match the actual split count exactly for multisplit
launches; BF16 output requires fused unrotation, which requires multisplit.
The public statistics buffer called `exp_sums` carries natural-log LSE.
`max_logits` remains ABI-valid and stream-tracked even where unused.

Consequences for the V2 port:

1. **Preserve ownership before changing dispatch.** At target
   `gpu/model_runner.py:669`, `init_attn_backend` receives
   `draft_layer_names` but no `active_layer_names`. In
   `gpu/attn_utils.py:196-225`, only `active_layer_names` filters builder
   ownership; `draft_layer_names` controls fast-prefill eligibility. The
   target runner can therefore construct a KVarN builder for draft layers
   unless the paired port explicitly excludes them. Draft
   `DraftModelSpeculator.set_attn` does use
   `active_layer_names=self.draft_attn_layer_names`. Duplicate owners are
   unsafe for mutable tails regardless of unchanged native schemas.
2. **Prepare draft resident slots before context writes.** Target
   `DFlash2Speculator` subclasses `DFlashSpeculator`. Its eager `propose`
   calls `_precompute_context_kv` before `_build_uniform_attn_metadata`.
   `qwen3_dflash.py:657-740` calls each draft attention impl's
   `do_kv_cache_update` directly for those context states. Current KVarN
   `do_kv_cache_update` consumes `_block_to_slot_t`, explicitly documented
   as mutated only by the metadata builder. The native scatter returns
   without writing when the mapped pool slot is invalid
   (`kvarn_hadamard_scatter_xe2.cpp:94-100`); it does not allocate slots.
   Fix metadata/slot preparation ordering in vLLM, without prematurely
   flushing rejected or incomplete history. An existing initialized pool
   alone does not establish a valid mapping for newly reached pages.
3. **Preserve exact accepted history.** DFlash's input kernel masks rejected
   context rows and null physical blocks with `PAD_SLOT_ID`, but the CPU
   metadata passed to generic builders is explicitly
   `seq_lens_cpu_upper_bound`. The native decode trusts the caller's
   `seq_lens` and cannot repair incorrect packing or CPU fill ownership.
   Port exact committed-history bookkeeping, transfer fences, destination
   residency invalidation, and cancellation/reuse cleanup with v05–v08.
4. **Noncausal semantics already have a Python path, not blanket native
   coverage.** Old KVarN advertises `supports_non_causal`; builder
   `kvarn_attn.py:1771-1793` assigns each noncausal query the full context
   length and disables the causal shared-dequant query-length shortcut.
   However `_native_verify_view` only admits one causal request with two
   or three query rows. DFlash2's arbitrary `1 + N` rows and noncausal
   drafting therefore do not automatically use that native view. Preserve
   and qualify the general path; extending native flattening is a separate
   measured optimization, with batching limits and exact masks tested.
5. **Select a compatible draft cache explicitly.** The prior performance
   review records `incoai/Qwen3.8-27B-DFlash2` as D128/KV8 with five
   noncausal sliding-window-2048 layers. This report did not refetch or pin
   its current config; reverify it during drafter selection. If those shapes
   are selected, they do not satisfy Q24/KV4/D256/no-window native decode
   or D256/G128 DPAS record-layout guards. Keep native compact K4V2 on the
   target and qualify an explicit BF16 draft cache first. Inheriting the
   target compact cache or merely widening guards is incorrect. A separate
   generic/natural KVarN draft path would need its own format, sliding-window,
   memory, quality, and speed qualification.

The DFlash2 speculator and model files are unchanged between frozen v0.31
and v0.32; their presence alone is not new support for this custom cache.
Relevant changed DFlash behavior includes
`36f397281295f5b58852a7eaf429b90348161079` (skip metadata builds where backends
support updates), `7d1d8660d620149bc4eadf795cbb80a1f884ddc2` (V2 restructuring),
and `ed7ae705a1f366c2008964af562a7543e91d934e` (int64 index mappings).
Keep those upstream changes. KVarN must decline any metadata-update shortcut
that bypasses required ownership/flush preparation until that lifecycle is
implemented and tested. None of those changes replaces a native KVarN op.

## Dependencies and folding

The owning paired feature is vLLM v05
`ef92dc5600af64103c01f97e3300b81c3a1083ee`; v06–v08 extend its prefix and
host lifecycle. Their resulting folded feature must remain compatible with
this k07 operator set and record representation. No kernel follow-up needs
folding. If replay discovers a build/schema compatibility repair, fold it
into one native-feature successor; do not create repair-only stack noise.
GDN correctness/test commits k02–k05 remain independent dependencies of the
hybrid workload rather than reasons to delete or fold native KVarN. k06's
ordinary attention controls remain useful because k07 changes shared
epilogues and build settings.

The native code stores bytes and executes attention; it does not own host
prefix validity or prove that every draft page was populated. Preserve the
v08 complete-page invariant at the context ceiling when replacing MTP with
DFlash, and adapt its producer semantics instead of assuming MTP-specific
cache-only forward behavior transfers directly.

## Performance preservation and validation

Preserve the split-16 four-column output-Hadamard reducer and the independently
64-byte-aligned K4V2 resident K/V block loads initially. Inspection confirms
the dispatches and scalar fallbacks remain in the assigned commit. Historical
v031 audit evidence reports about 3.03% geometric improvement for six short
native cells for the reducer, and roughly 39–51% shorter native K4V2 spans
at 16K/65K for resident loads, with adverse cells and repeatability limitations
explicitly recorded there. These are historical native event spans, not fresh
V2 serving gains. No current benchmark was run in this audit. Do not drop the
optimizations without controlled comparisons, or claim they make DFlash2
faster merely because tests pass.
