## Requirement and minimum retained change

**KEEP**, folding the two load helpers, their guarded call sites and the
independent regression into k08
`9bb1e2d428b8a25b262c0cd6704614bdf6ee3ad8`, alongside the compact-record
extension k09 `f26ef2323399ab410299db5c8caec41c8d63215a`.
Final release retention remains subject to the bounded correctness and
controlled performance gates below.

For the released Brutus / Arc Pro B70 geometry D256/G128, Q24/KV4, packed
K4V2 history shares one attention operation with resident rotated FP16 pages.
k11 reads those resident pages through the existing Xe2 block-copy machinery,
reducing the measured cost of resident-heavy K4V2 attention. Its entire delta
is in `csrc/xpu/attn/xe_2/collective/kvarn_decode_mainloop.hpp` and
`tests/flash_attn/test_kvarn_k4v2_xpu.py`: 196 insertions, 10 deletions.
It changes no record encoding, history policy, pool ownership, softmax
arithmetic, split assignment, reducer or public schema. There is no later
released kernel commit superseding it.

Retain the existing eager V1 target/draft MTP2, vision, formats, context and
scheduler configuration. This optimization does not add format or geometry
admission. K4V4 keeps its scalar resident loader; ordinary FP16/BF16 and
other supported attention paths remain release regression controls.

## Guard and indexing revalidation

The following observations refer to immutable released source at k11, which
must survive the k08 fold; the unpatched target itself lacks these bindings.

- `kvarn_decode_xe2.cpp:180–246` requires contiguous query/output
  `[B,24,256]`, B in 1–12, contiguous packed `[blocks,4,record_bytes]`
  records with sufficient width and uint32-aligned record stride, int32
  metadata, and matching contiguous half K/V pools `[slots,128,4,256]`.
  It retains the variant-18 and DPAS-layout gates. Metadata values such as
  valid page/slot IDs and sequence bounds remain scheduler-owned invariants;
  shape checks are not validation of arbitrary device metadata.
- `kvarn_decode.hpp:758–764` constructs fixed tail strides in half elements:
  slot 131072, token 1024, head 256. Therefore width/pitch/height are
  512 bytes / 2048 bytes / 128 rows, and slot/head byte offsets are
  262144/512. The inherited contiguous-pool checks make those strides true
  for both K and V. k11 tests each base pointer independently for 64-byte
  alignment and additionally requires `ValueBits == 2`. Offset 32 half
  elements stays aligned; offset 1 half element falls back independently
  for that tensor. No new restriction rejects a legal contiguous offset view.
- `load_tail_k_fragment` constructs a `(128,256)` surface with
  `(token_stride,1)` strides and K64×D64 tiles; `load_tail_v_fragment`
  constructs `(256,128)` with `(1,token_stride)` and D32×K64 tiles.
  `logical_tile & 1` selects the page half; dimension tile coordinates
  select the same columns as scalar indexing. Both use the base copy's
  thread partition and `reorder(loaded,dst)` to produce MMA-B fragments.
  The prior host address-domain enumeration is retained evidence, not a new
  compiled lane-layout test in this audit.
- K block copying requires `slot >= 0 && block_tail_k`; V copying is
  inside the resident branch and checks `block_tail_v`. Packed K/V retain
  their original unpackers and scale frames, while each unaligned resident
  tensor takes its scalar loader. The record cursor refreshes for even
  tiles and odd split starts. Ragged rows exit before page-table access;
  partial valid tiles retain allocated storage and score masking. This
  does not establish immunity to NaNs in unused resident values.
- `kvarn_decode_xe2.cpp:265–301` retains exact multi-split scratch extents:
  half `[B,24*splits,256]` partials and float `[B,24,splits]` statistics,
  contiguous and non-aliasing with each other/output. One-split direct output
  can reuse larger scratch because it does not consume it; fused unrotation
  requires more than one split. The public two-statistics ABI remains: the
  first stores natural-log LSE and the second is validated and stream-tracked
  but unused. k11 changes none of this. Replaying its helpers must not weaken
  these guards or conflate allocation capacity with logical split stride.

The added `test_resident_pages_and_offset_tail_views_match_independent_attention`
covers bits 2/4, splits 1/24/32, lengths 127/257/4001/4223, permuted physical
pages/resident slots and K/V offsets `(0,0),(32,32),(1,0),(0,1),(1,1)`.
It compares against independent FP32 attention (`rtol=0.006`, `atol=0.002`),
requires finite output, exact aligned/fallback parity and unchanged pool
backing buffers. These are meaningful tests of both independent fallbacks.
They do not directly test fused split-16 output.

## Dependencies and k10 interaction

k08 owns the KVarN native ABI and feature; k09 supplies `ValueBits=2`,
width-aware records and compact K4V2 dispatch. Companion v10
`80d5166fcb0b7935f3f95b8d343e3e669940261f`, folded with the paired vLLM
KVarN feature, remains necessary to reach that path with correct layout,
resident ownership and dispatch. k11 introduces no additional Python API,
operator schema or independent vLLM patch.

k10 `c69cfad0586bb0eda4218fae495f446ae0e845bc` is the historical parent,
but not a functional prerequisite. It changes only `kvarn_decode.hpp`:
the `unrotate_output` / `num_kv_splits == 16` arm selects
`KVarNReduceSplit16FourColumnOutputHadamardKernel`. k11 changes the attention
producer's resident loads, with the same fragments and scratch contract.
Thus it can be retained if k10's independent retention gate rejects k10;
dropping the reducer must not accidentally drop these load helpers.
Conversely, k11's 24/32-split historical timing cells cannot certify the
combined split-16 reducer or rescue k10's recorded repeatability concerns.
Hold k10 fixed in a with/without-k11 comparison and k11 fixed in k10's gate.

The vLLM target's `requirements/xpu.txt:23` still declares kernels 0.1.14.1;
the manifest deliberately selects 0.1.15. The release's
[paired compatibility review](../pair-compatibility.md) explicitly documents
that source-build exception, unchanged Torch 2.13/oneAPI 2026.0 line and
schema evidence, with actual target/MTP/vision qualification still required.
k11 introduces no further dependency exception and does not discharge that
native qualification gate.
