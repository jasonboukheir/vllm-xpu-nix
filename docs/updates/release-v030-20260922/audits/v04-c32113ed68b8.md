## Requirement and effective contribution

The original residual branch of
`vllm/model_executor/determinism/batch_invariant.py:rms_norm_batch_invariant`
calls `_custom_ops.fused_add_rms_norm` and returns its two mutated inputs.
v04 adds `_fused_add_rms_norm_kernel`: one Triton program per row, fixed
1,024-element reduction blocks, FP32 addition and variance accumulation, and
separate output and residual allocations. Changing the number of unrelated
rows changes the grid without changing each row's reduction tree. The inputs
remain unchanged; optional weights, contiguous conversion and restoration of
the original dimensions are supported.

The required observable behavior is exact replay and equality for the same
input/residual row across different batches, plus the preserved functional
result and arithmetic contract. The helper normalizes the unrounded FP32
sum, while returning the residual rounded to the activation dtype. The native
XPU vector and scalar paths round the sum to activation dtype before computing
variance. Pinning only their launch therefore would not reproduce this helper.

The generic caller remains `RMSNorm.forward_cuda`, also used by
`RMSNorm.forward_xpu`, under `VLLM_BATCH_INVARIANT`. Full XPU batch-invariant
mode has additional requirements, including the Triton attention backend;
this normalization fix alone does not establish full-model invariance.

Later v05 `fcab69494f1719e91e416aace17ef6ad501fe900` adds the independent
XPU request-stability caller in `GemmaRMSNorm.forward_native`. Its callback
uses FP32 `weight + 1.0` and calls this helper. The released
`vllm/model_executor/determinism/request_stable_linear.py:523-570` passes
the whole validated packed tensor to `request_invariant_apply_once` before
its canonical-row fallback. `GemmaRMSNorm.forward_xpu` bypasses the fused
native kernel when the scoped policy and request slices are present.

That policy explicitly selects the AEON model/revision
`jasonboukheir/Qwen3.8-27B-AEON-Ultimate-Uncensored-BF16-W4A16-AutoRound` /
`6b0622f4354481d5d04577d48ba0db844efc1330`, BF16 compressed-tensors, eager
V1, compact K4V4/K4V2, language-only, no speculation/prefix caching, and
restricted parallelism. It is inactive for the current RedHat K4V2/MTP2/vision
profile. Its inactivity in that profile is not evidence that its existing
supported behavior may be discarded.

Both files changed by v04 are byte-identical between v04 itself and the full
released vLLM tip; path history over the complete local range contains only
v04. No release-only follow-up supersedes or repairs this implementation.

## Minimum residual and dependencies

1. Keep v04's functional row-local implementation and its XPU weight/shape
   handling. Narrow the replaced residual branch to XPU; retain upstream's
   original non-XPU native residual dispatch and contract. Preserve the
   non-residual path. The module already imports `current_platform`.
2. Restore upstream's direct native CUDA residual regression. Add separate
   XPU helper coverage in the existing suite with an XPU-capable marker,
   rather than replacing the CUDA test or silently skipping on Brutus.
   Include a dispatch check so the platform narrowing remains enforced.
3. Keep v05's scoped Gemma caller and its v04 dependency together in the
   reconciled inventory. Do not route that mixed-dtype, functional caller to
   the native in-place operator merely because generic CUDA is restored.
4. No companion schema/API change is required. No later repair must be folded
   into v04; its platform narrowing and tests belong in its one surviving
   independent correctness commit. It has no source dependency on v03 despite
   the parent relationship. Kernel k01's deterministic W4A16 matmul does not
   establish normalization invariance and cannot replace this requirement.

A smaller native fixed-launch substitute is not ruled out in principle, but
would need evidence for rounding, optional/FP32 weights, mutation/aliasing,
strides and caller behavior. It is not justified for this release merely by
a smaller textual delta. No DFlash implementation or V2 port is needed here.

## Validation and release gates

Observed during this audit: patch ID and source identities verified; upstream
CUDA fix ancestry checked; exact relevant old/target/released implementations
compared; target kernel additions inspected; final local caller and policy
traced. Both candidate source worktrees remained clean. No GPU execution or
new timing measurement was performed.

The existing v04 residual test covers H512/H4096, FP16/BF16, one row versus
4/300 rows and 16 seeds, but retains `@skip_if_not_cuda`. At the exact target,
`tests/v1/determinism/utils.py:69-72` requires CUDA >= SM80 for that marker;
running the unchanged test on Brutus can yield only skips. Its reference also
starts from an activation-dtype rounded residual and uses a loose BF16
tolerance, so it does not tightly specify v04's FP32-add normalization.

Required after the parent adapts and builds the actual release package:

- Execute XPU residual-helper tests at batch sizes 1, 4, 255, 256, 257 and 300,
  with H4096 and relevant production widths. Compare upstream native and the
  retained helper under matched inputs to distinguish the still-needed
  guarantee. Vary row placement and aligned/strided inputs; require exact
  replay and cross-batch equality for both outputs of the helper.
- Assert input preservation and output non-aliasing. Cover `weight=None`,
  noncontiguous weights/views, higher-rank flattening, FP16/BF16, and BF16
  activations with FP32 Gemma `weight + 1`. Use an FP32-add FP32-reduction

- Verify restored non-XPU routing and retain the native CUDA regression;
  record hardware-unavailable CUDA checks honestly instead of implying they

- Exercise the preserved scoped AEON request-stability caller, including
